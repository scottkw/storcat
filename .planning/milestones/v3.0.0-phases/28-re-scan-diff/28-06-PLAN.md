<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: How to put this milestone in front of CI</name>
  <decision>Whether to push the branch and open a pull request against `main`, or to push local `main` directly to `origin/main`.</decision>
  <context>
`build.yml` triggers on both a push and a pull request against `main`. Either route produces a real
Actions run, which is what COMPAT-06 needs. They differ in consequence, and the difference is not
reversible in the same way.

Local `main` is roughly 100 commits ahead of `origin/main`, covering Phases 22 through 28 — the entire
Go/Wails rewrite. This is a large, one-way publication of the milestone, and it is genuinely the user's
call, not a step to perform silently inside a verification checklist.

Two further consequences worth stating plainly before choosing:

- A push to `main` also triggers release-please, which opens or updates a release PR. It does NOT create
  a tag and does NOT fire `release.yml`. Signing and notarization stay unproven either way unless a tag
  is separately cut and that release run is observed.
- This project's GSD worktrees fork from `origin`. While local `main` stays unpushed, executor worktrees
  for future work start from stale code. Pushing resolves that; a PR branch resolves it only for that
  branch.

Project git norms apply regardless of choice: no force-push, no `--no-verify`, and no history rewriting.
  </context>
  <options>
    <option id="pr-branch">
      <name>Push a branch and open a PR against `main`, without merging</name>
      <pros>Produces a real, citable Actions run on real native runners; defers the "should local main go to origin" decision; nothing lands on `origin/main` until the user says so; reviewable diff.</pros>
      <cons>`origin/main` stays ~100 commits behind, so GSD worktrees keep forking from stale code; the milestone remains unpublished; release-please is not exercised.</cons>
    </option>
    <option id="push-main">
      <name>Push local `main` to `origin/main`</name>
      <pros>Produces a real Actions run; publishes the milestone; unblocks worktrees forking from `origin`; exercises release-please's PR-opening behaviour, which is the real precursor to a tagged release.</pros>
      <cons>A large one-way publication of ~100 commits; if `build.yml` fails, the failure is already on `main`; opens a release-please PR that will need attention.</cons>
    </option>
    <option id="push-main-then-tag">
      <name>Push local `main`, then also cut a `v3.0.0` tag to exercise `release.yml`</name>
      <pros>The only route that can prove any part of the signing/notarization half — macOS signing and notarization would genuinely run.</pros>
      <cons>Windows signing would still SKIP with a warning because CRED-04/CRED-05 are unprovisioned, so the Windows half stays unproven regardless; cutting a release tag is a product decision beyond this phase's scope; a tagged release is far harder to walk back than a push.</cons>
    </option>
  </options>
  <resume-signal>Select: pr-branch, push-main, or push-main-then-tag.</resume-signal>
</task>
