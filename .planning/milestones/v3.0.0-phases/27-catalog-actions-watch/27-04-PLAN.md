  <action>
Create the app's first menu primitive. It is **conditionally mounted by its parent** — the parent renders it only while open, so this component may assume `isOpen` is true whenever it renders and must not carry an internal `if (!isOpen) return null` gate. That is the opposite of `SettingsDialog`'s always-mounted shape and is the single most likely thing to be copied wrongly; `27-UI-SPEC.md` locks it because a menu has no exit animation whose teardown the hook would need to observe.

**Exported types.**
- `MenuItemSpec` — `id: string`, `label: string`, `danger?: boolean`, `dividerBefore?: boolean`, `onSelect: () => void`.
- `MenuProps` — `isOpen: boolean`, `onClose: () => void`, `triggerRef: React.RefObject<HTMLButtonElement | null>`, `items: MenuItemSpec[]`, `id: string`, `ariaLabel: string`.
- Default-export the component.

**Shared behavior.** Call `useModalBehavior` with `isOpen`, `onClose`, `initialFocusRef` pointing at the first item's button ref, and `scrollLockSelector: '.ws-details-overflow'`. That selector is deliberate and is `27-CONTEXT.md`'s literal mechanism for "the menu skips scroll-lock": the hook always sets `overflow: hidden` on *some* element, so aiming it at a 22×22 icon button with no internal scroll makes the assignment a functional no-op — configuration, not a fork of the hook. `.ws-details-overflow` is unique in the DOM because the details panel renders as one component instance regardless of pane-versus-drawer tier. Do not pass `.ws-root`, and do not modify the hook.

**Positioning.** In a `useLayoutEffect` keyed on `isOpen`, read `triggerRef.current.getBoundingClientRect()` into local state and apply it as inline styles on the menu element: `top = rect.bottom + 6` and `right = window.innerWidth - rect.right`. Right-edge alignment computed from the trigger's own screen position is what makes this correct whether the details panel sits on the app's left or right side under the rail-position setting. `position: fixed` comes from `.ws-menu`; it is required rather than `absolute` because the details panel's `.pane-scroll` region has `overflow-y: auto` and would otherwise clip the menu or scroll it away from its anchor.

Implement **no viewport-collision or flip-to-open-upward logic.** `27-UI-SPEC.md` resolves this explicitly: three short items totalling roughly 100px, opening downward from a button that always sits near the top of the details panel in either layout tier, has no realistic path to overflowing the bottom of the window at any size this app supports. Building flip logic for a case that cannot occur would be speculative generality. This is recorded as a `backstop` truth in this plan's `must_haves` — reasoned from the app's real geometry, not proven by an automated boundary sweep — so it is honestly flagged rather than silently claimed.

**Roving tabIndex.** Hold an `activeIndex` state initialized to 0 and an array of item button refs. Each item gets `role="menuitem"` and `tabIndex={index === activeIndex ? 0 : -1}` — a roving index, not a single container tab stop, because arrow keys must move focus between individual items per `27-CONTEXT.md`'s locked keyboard contract. On `keydown` within the menu: ArrowDown advances with wraparound to 0 past the last item; ArrowUp retreats with wraparound to the last item; both `preventDefault` and call `.focus()` on the newly active item's ref. Enter and Space activate the focused item (`preventDefault`, then the item's `onSelect`). Do not handle Escape here — the shared hook already owns it, and a second handler would double-fire.

**Click-outside.** The shared hook provides no scrim and no pointer listener, so add one here: a `document` `pointerdown` listener registered in a `useEffect` while open, closing the menu when the event target is outside **both** `containerRef.current` and `triggerRef.current`. Excluding the trigger is what lets the trigger's own `onClick` perform the toggle-closed without the listener racing it into a close-then-reopen. Remove the listener in the effect cleanup.

**Markup.** A single `<div ref={containerRef} className="ws-menu" role="menu" id={id} aria-label={ariaLabel} style={{ top, right }}>` containing, for each item in order: an optional `<hr className="ws-menu-divider" role="none" />` when `dividerBefore` is set, then a `<button type="button" role="menuitem" className={danger ? 'ws-menu-item ws-menu-item-danger' : 'ws-menu-item'}>`. Each item's `onClick` calls `onSelect()` — the *caller* is responsible for closing the menu, because "close then open a dialog" and "close then run an action" are the caller's sequencing decisions, not this primitive's.

Every item is always enabled. `27-UI-SPEC.md` resolves the concurrency question explicitly: the three actions operate on one already-selected catalog file while a running scan only ever writes a brand-new file on completion, so no item is disabled by scan state and this component takes no scan-related props.

**No icons.** The three labels are unambiguous on their own, and `22-UI-SPEC.md`'s icon library is a deliberately minimal five SVGs. This is `27-CONTEXT.md`'s discretion item resolved toward the smaller surface.
