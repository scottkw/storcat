# Phase 27 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Source of truth:** `27-CONTEXT.md`'s 16 locked decisions across 4 areas (catalog identity/rename, destructive actions/crash safety, actions menu/confirmation UI, file watching) — this phase has no handoff-mockup authority (the original `design_handoff_storcat_ui/` 1a Workspace demo predates catalog actions and watching entirely; there is no prototype markup for a `⋯` menu, a rename field, a delete confirmation, or a watching indicator to transcribe). Every geometry/color/copy decision below is therefore Claude's own design work, built to slot into the already-locked token system rather than inventing a second one.
>
> **All base tokens, the type scale, the 1/2/3/5/6/7/8/10/12/14/16/18/20/22px spacing scale, radii, shadows, density tokens, and the `--z-details-drawer/--z-overlay/--z-dialog` z-index scale are locked in `22-UI-SPEC.md`; rail/tree/details/status-bar visuals are locked in `23-UI-SPEC.md`; the shared `useModalBehavior` hook's four-behavior contract is locked in `24-UI-SPEC.md`; the toggle-switch control is locked in `25-UI-SPEC.md`; the centred-dialog shell pattern (scrim, header, footer, `100ms` fade) is locked in `26-UI-SPEC.md`.** This document does not restate or renegotiate any of them. It specifies four new surfaces built from those locked pieces: the catalog-actions menu off the `⋯` button, the rename dialog, the delete-confirmation dialog (which activates the destructive color `22-UI-SPEC.md` already reserved and named "Phase 27"), and the status-bar watching indicator.
>
> **One color decision is not new — it is this phase fulfilling a two-phases-old reservation.** `22-UI-SPEC.md`'s Color section already declared `Destructive | #e5534b (theme-independent, fixed across all 11 themes) | Declared this phase; not visibly used ... delete button is Phase 27`, and its Status colors table already named `#e5534b` for "destructive buttons (Phase 27)". This document does not pick a new destructive hex — it formalizes that already-reserved literal into two named CSS custom properties (`--danger`, `--ondanger`) so this phase's three consumers (menu item, dialog button, error banners) share one declaration instead of three copies of a hex literal.

## Color

No new base or per-theme tokens. This phase activates the destructive color `22-UI-SPEC.md` already reserved, formalized into two named custom properties declared once in `workspace.css`:

```
--danger:   #e5534b   /* theme-independent, fixed across all 11 themes — */
--ondanger: #ffffff   /* the exact literal already used 3x in workspace.css   */
                       /* (parse-error text, scan-error badge, error log lines) */
```

Both are literal, not per-theme-derived — this is Claude's Discretion resolution (`27-CONTEXT.md`): the app already has two theme-independent status colors (`#e5534b` error, `#f0b429` warning, both declared "fixed across all 11 themes" in `22-UI-SPEC.md`'s Status colors table), and a third status-family color that suddenly became per-theme-derived would be the one inconsistent member of that set. `--ondanger` is a fixed white, not a computed `lum()`-based choice like `--onac` — `#e5534b` sits in a narrow enough luminance band that white text clears contrast reliably in every context this phase uses it (a filled button, a filled menu-item background never occurs — see below), unlike `--ac`, which spans Gruvbox orange to GitHub blue and genuinely needs the per-theme luminance check.

| Role | Value | Usage |
|------|-------|-------|
| `--danger` | `#e5534b` (fixed) | Delete-confirmation dialog's primary button fill; "Delete catalog…" menu item text; both dialogs' inline error-banner text |
| `--ondanger` | `#ffffff` (fixed) | Text on the delete-confirmation dialog's filled primary button |
| `rgba(229, 83, 75, .16)` | literal (fixed) | "Delete catalog…" menu item's hover/focus background — reuses the exact tint literal already declared at `workspace.css:1034` for the scan-error badge, not a new value |
| `--ac` | theme-dependent | Rename dialog's primary "Rename catalog" button fill (reuses the standard accent-filled-button treatment every other primary action in this app uses — rename is not destructive) |
| `--hov` | theme-dependent | "Rename catalog…" / "Duplicate catalog" menu items' hover/focus background (the existing generic row-hover token, unchanged from its use elsewhere) |

**Accent reserved for (additive to Phases 22–26's lists — nothing removed):**
- Rename dialog's primary "Rename catalog" button fill (`--ac`)
- Nothing else new this phase — the destructive dialog deliberately does NOT use accent anywhere; a delete confirmation with an accent-colored anything would visually compete with the one color that actually matters here

**Destructive reserved for (new this phase — the reservation `22-UI-SPEC.md` named two phases ago):**
- Delete-confirmation dialog's primary button fill + text
- "Delete catalog…" menu item's text and hover tint
- Inline error-banner text in both dialogs (a write/trash failure is itself a form of "something went wrong," the same semantic family as the existing parse-error/scan-error uses of this color — not a new color-meaning, the same one)

## Z-Index

**New value added to the locked scale, filling the gap `22-CONTEXT.md`'s scale was deliberately built with room for:**

| Layer | z-index | CSS var |
|---|---|---|
| Details drawer (narrow-tier overlay) | 100 | `--z-details-drawer` |
| **Catalog-actions menu (new)** | **150** | **`--z-menu`** |
| Create slide-over / ⌘K palette | 200 | `--z-overlay` |
| Rename / delete dialogs | 300 | `--z-dialog` (reused, not new — same tier as Settings) |

**Why the menu needs its own tier, not `--z-overlay` or a bare re-use of `--z-details-drawer`:** the menu is `position: fixed` (see below — it must escape the details panel's own `overflow-y: auto` scroll region, which would otherwise clip or scroll it away from its anchor), so it is never contained by the narrow-tier drawer's stacking context and must out-rank it explicitly. It must never compete with a real modal (palette/create/Settings) for stacking, because — per the established "one overlay owns the screen" model (`24-UI-SPEC.md`/`25-UI-SPEC.md`/`26-UI-SPEC.md`) — the details panel that anchors this menu is itself unreachable while any of those is open, so the two can never be visible simultaneously; `150` only needs to beat the drawer, giving future phases room both above and below it, the same forward-looking spacing the original scale (100/200/300) was built with.

Rename/delete dialogs reuse `--z-dialog: 300` unchanged — they are dialogs, the same category as Settings, not a new tier.

## Catalog Actions Menu (ACT-01)

**Trigger:** the existing `OverflowButton` in `frontend/src/components/workspace/DetailsPanel.tsx:43-68` — unchanged glyph/geometry (22×22px, `⋯`, `aria-label="Catalog actions"`). This phase adds: `aria-haspopup="menu"`, `aria-expanded={isOpen}`, `aria-controls="ws-catalog-actions-menu"` when open, and an `onClick` that toggles the menu (a second click on an already-open trigger closes it — standard disclosure-button behavior, not previously needed anywhere else in this app since no other trigger in this codebase toggles the same overlay both ways).

**Mount pattern:** rendered only while open (unlike the always-mounted Settings/palette dialogs — a menu has no exit animation to preserve, so conditional mounting is the simpler correct choice here, not a deviation needing justification).

**Positioning — `position: fixed`, computed once at open, not live-following:**
- Read the trigger button's `getBoundingClientRect()` in a `useLayoutEffect` keyed on open-state.
- `top = trigger.bottom + 6` (6px gap, existing scale value).
- `right = window.innerWidth - trigger.right` (right-edge-aligned to the trigger's right edge — safe regardless of whether the details panel is on the app's left or right side per the rail-position setting, since it's always computed from the trigger's own screen position, never the panel's).
- **No viewport-collision/flip logic.** Three short items (≤ ~110px each including the delete divider) at a maximum height of roughly 100px, opening downward from a button that always sits near the top of the details panel (in either the pane or narrow-tier drawer layout) never has a realistic path to overflowing the bottom of the window on any screen size this app supports. Building flip-to-open-upward logic for a case that cannot occur in this app's actual layout would be speculative generality, not defensive design — see UI Considerations E1/overflow for the explicit boundary this claim rests on.
- `position: fixed` is required (not `absolute`) specifically because the details panel's own `.pane-scroll` region has `overflow-y: auto` — an absolutely-positioned menu nested inside it would be clipped/scrolled with the pane instead of floating free.

**Panel:** `min-width: 160px`, `width: max-content`, `border-radius: 9px`, `background: var(--p)`, `border: 1px solid var(--l)`, `box-shadow: 0 18px 40px rgba(0,0,0,.5)`, `padding: 6px 0`. `role="menu"`, `id="ws-catalog-actions-menu"`, `aria-label="Catalog actions"`.

**Items** (`role="menuitem"`, `tabIndex: -1` except the currently-focused item at `0` — roving `tabIndex`, not a single container tab-stop, since arrow keys must move focus between individual items per `27-CONTEXT.md`'s locked "arrow-key navigation"):

| Order | Label | Padding | Hover/focus bg | Text color | Action |
|---|---|---|---|---|---|
| 1 | "Rename catalog…" | `6px 10px` | `--hov` | `--tx` | Closes menu, opens Rename dialog |
| 2 | "Duplicate catalog" | `6px 10px` | `--hov` | `--tx` | Closes menu, runs duplicate immediately (no dialog) |
| — | 1px `--l` divider, `margin: 4px 0` | — | — | — | Visual-only separation before the destructive item |
| 3 | "Delete catalog…" | `6px 10px` | `rgba(229,83,75,.16)` | `--danger` | Closes menu, opens Delete-confirmation dialog |

**No icons.** `22-UI-SPEC.md`'s icon library is 5 SVGs total, deliberately minimal; adding 3 new glyphs for a 3-item text menu that is already unambiguous from its labels alone would grow that budget for no comprehension gain — this is Claude's Discretion (`27-CONTEXT.md` leaves icon inclusion open), resolved toward the smaller surface area.

**Keyboard:** ArrowDown/ArrowUp move focus between the three items (wrapping at the ends); Enter/Space activates the focused item; Escape and click-outside close (Escape via the shared hook below; click-outside is this component's own addition — see Interaction contract). Focus restores to the `⋯` trigger on close, matching every other overlay in this app.

**`useModalBehavior` wiring:**
```
useModalBehavior({
  isOpen,
  onClose,
  initialFocusRef: firstMenuItemRef,
  scrollLockSelector: '.ws-details-overflow',
})
```
`scrollLockSelector` deliberately points at the trigger button itself, not `.ws-root` or any scrollable region. This is the literal mechanism `27-CONTEXT.md` names ("the hook exposes `scrollLockSelector`, so this is configurable, not a fork") — the hook always sets `overflow: hidden` on *some* element; pointing it at a 22×22px icon button with no internal scroll makes that assignment a functional no-op, which is exactly "skip scroll-lock" without touching the hook's four-behavior implementation. `.ws-details-overflow` is a safe, unique selector: the details panel renders as one component instance regardless of pane/drawer tier (`22-UI-SPEC.md`'s Layout contract: "the same component, not a duplicate"), so exactly one such button exists in the DOM at a time.

**Click-outside is NOT provided by `useModalBehavior`** (it has no scrim and no pointer listener — only Settings/palette/create get "outside click" for free because their scrim div's own `onClick` does it). This component adds its own: a `document` `pointerdown` listener (registered only while open) that closes the menu if the event target is outside both `containerRef` and the trigger button. This is new interaction logic specific to this component, called out explicitly so it is not silently skipped on the assumption the shared hook already covers it.

**Interaction with an active scan:** none. The menu's three actions all operate on one specific, already-selected catalog file; a running scan only ever writes a brand-new file on completion. No menu item is disabled while a scan is running (see UI Considerations E1/partial).

## Rename Dialog (ACT-02)

Reuses the exact centred-dialog shell pattern `26-UI-SPEC.md`'s Settings dialog established (scrim `rgba(4,6,9,.62)` at `--z-dialog`, `100ms` fade-only transition, panel `border-radius: 12px`, `background: var(--p)`, `border: 1px solid var(--l)`, `box-shadow: 0 30px 70px rgba(0,0,0,.6)`) at a narrower **440px** width, no fixed `max-height` (content is always short enough that one never applies).

**One shared shell component** backs both this dialog and the delete-confirmation dialog below — `27-CONTEXT.md`'s "do not write a second overlay implementation" instruction, already applied to the menu, applies equally here: build one small dialog-shell component (header/body/footer slots) and pass each consumer's own title/body/footer content into it, rather than two near-duplicate 440px-panel implementations. One shared `100ms` scrim-fade keyframe, declared once for both (project convention: this keyframe is this shared shell's own declaration, distinct from the palette's and Settings' — not reused verbatim from either, since it is a genuinely different consumer, even though the values are identical).

**Header (50px, 1px bottom border `--l`):** title "Rename catalog" (15px/600) + `×` close (16px `--dm`, `aria-label="Close"`, `margin-left: auto`) — no `⌘,`-style hint, since this dialog has no independent keyboard shortcut; it is only reachable via the menu.

**Body (padding 20px, flex column gap 16px):**
- Label "Title" (12.5px/500).
- Text `<input>`: `height: 30px; border-radius: 7px; background: var(--p2); border: 1px solid var(--l); padding: 0 10px; font-size: 12.5px` (Sans, 400 weight — see Typography note above). **Pre-filled with the catalog's current title** (already resolved via the existing HTML-then-filename fallback for a catalog with no `title` field yet). On mount, focus lands in this field AND its text is selected (`inputRef.current.select()`, called once in the same effect that sets `initialFocusRef`) — so typing immediately replaces the pre-filled value instead of requiring a manual select-all first, a small, low-risk affordance worth locking so the executor doesn't have to guess it.
- Enter (while the field has focus) submits, identical to clicking the primary button. `27-CONTEXT.md`'s "Enter commits" locked decision.
- Inline error banner (12px, `--danger`, line-height 1.5) rendered below the field only after a failed write — see Copywriting Contract for the exact string. The dialog stays open, the field keeps the user's edited value, and the primary button re-enables so the user can retry without retyping.

**Footer (56px, `--p2` background, 1px top border `--l`, buttons right-aligned, gap 8px):**
- Secondary: "Keep original title" — `height: 32px; padding: 0 16px; border-radius: 8px; background: transparent; border: 1px solid var(--l); color: var(--tx); font-size: 12.5px; font-weight: 600`. Closes with no write, identical to `×`/Escape/scrim-click.
- Primary: "Rename catalog" — same geometry, `background: var(--ac); color: var(--onac); border: none`. **Disabled when the trimmed field value is empty** (an empty title has no sensible fallback the way an empty filename-root does in Settings — there is nothing to fall back to once a `title` field exists on disk). No other client-side validation; this app does not pre-validate text fields beyond the empty check already established for required fields elsewhere.

**On success:** the catalog's title updates in `state.catalogs` immediately (optimistic — no wait for a full rail re-list), so the rail row and the details panel both reflect the new title in the same frame the dialog closes, consistent with this app's established "no spinners, optimistic UI" rule (`26-UI-SPEC.md`'s Persistence Contract).

## Delete-Confirmation Dialog (ACT-04, ACT-05)

Same shared 440px shell as the rename dialog above. Two sub-states in one mounted instance (confirm → error), never two separate dialogs — matching the "same component, swap the body" pattern `25-UI-SPEC.md`'s create-flow states already established.

**Header:** title "Delete catalog" (15px/600) + `×` close, same as rename.

**Confirm body (padding 20px, flex column gap 16px):**
1. Lead sentence (11.5px, `--tx`, line-height 1.5): `"This moves the file(s) below to the Trash — you can restore them from the Trash until it's emptied."` Load-bearing copy: it is the only place in this dialog that tells the user the action is recoverable, which is exactly why this project's requirements explicitly reject a "type to confirm" gate (`REQUIREMENTS.md` Out of Scope: "Files go to Trash and are recoverable — a confirmation dialog is proportionate").
2. Path box 1 (always present): label "Catalog (.json)" (11.5px/500, `--dm`) above a mono path box — `background: var(--ch); border: 1px solid var(--l); border-radius: 9px; padding: 8px 10px; font-size: 11.5px; word-break: break-all` — showing `catalog.path` **verbatim, in full, never ellipsized**. A destructive confirmation's one job is letting the user verify exactly what they're about to remove; truncating the one piece of evidence that answers "is this the right file?" would undermine the confirmation itself.
3. Path box 2 (**only rendered when `catalog.hasHtml` is true — omitted entirely, not greyed, when it is false**, matching this app's established "no button/row whose only possible outcome is inapplicable" convention already used twice by the Footer component): label "HTML (.html)" above the same box treatment, showing the paired `.html` path (same-directory, same-basename convention already established in `internal/search/service.go`/`app.go`).
4. Checkbox row (only rendered alongside path box 2 — i.e., only when an `.html` exists): native `<input type="checkbox">` with `accent-color: var(--ac)` (a progressive-enhancement CSS property; unsupported WebKitGTK versions fall back to the browser's own native checkbox rendering, a cosmetic-only degradation, not a functional one — same class of low-risk platform variance this project already tracks in `WINDOWS.md` rather than blocking on), wrapped in a `<label>` with text "Also delete the matching .html" (12.5px/500, `--tx`). **Checked by default.** Unchecking it leaves the `.html` file untouched on disk.

**Confirm footer:**
- Secondary: "Keep catalog" — same outline treatment as rename's "Keep original title."
- Primary (destructive): `background: var(--danger); color: var(--ondanger); border: none; font-weight: 600`, same 32px/8px-radius geometry. **Label reflects exactly what will happen**, resolved dynamically rather than a generic "Delete":
  - No `.html`, or `.html` exists but the checkbox is unchecked: **"Move to Trash"**
  - `.html` exists and the checkbox is checked: **"Move both to Trash"**
- While the Trash operation is in flight: primary button `opacity: 0.7`, both buttons `disabled` — reuses the exact busy-state treatment `DetailsPanel.tsx`'s existing `Footer` component already applies to `openBusy`/`revealBusy` (no spinner, per this project's no-spinners rule).

**Error sub-state (ACT-05 — same mounted dialog, body/footer swapped, path boxes and checkbox stay visible above the error for context):**
- Error banner (12px, `--danger`, line-height 1.5) below the path boxes: `"Couldn't move [title] to the Trash: [system error message]."` — the literal OS/wastebasket error surfaces, not a generic fallback string, per `27-CONTEXT.md`'s "surfaces the real error" requirement.
- Footer swaps to: secondary **"Keep catalog"** (unchanged — closes with nothing deleted) and primary **"Try moving to Trash again"** (destructive-styled, unchanged fill, re-attempts with the same checkbox state). **There is no third button, no "delete permanently instead" link, and no wording anywhere in this state that implies a fallback exists.** This is ACT-05's explicit, non-negotiable requirement — the constraint that governs every word in this sub-state, not just its primary action.

**On success:** the deleted catalog (and duplicate, on that path) both resolve through the same `catalogs:changed`-driven rail re-list the file watcher establishes (per `27-CONTEXT.md`'s Integration Points — `CatalogRail.tsx:50-53`'s existing directory effect is the one reusable refresh path), not a bespoke second refresh mechanism. If the deleted catalog was the current selection, `state.currentCatalogId`/`state.selected` clear, and the details panel falls back to its existing "nothing selected" placeholder (already built, Phase 22) — no new empty state is needed here.

## Watching Status-Bar Indicator (WATCH-01)

Extends `frontend/src/components/workspace/StatusBar.tsx`'s existing conditional-segment pattern (the `●`-prefixed scan segment) with a second, independent conditional segment — both can be visible simultaneously (watching a directory while a scan into that same directory is also running is a normal combination, not an edge case to prevent).

**Structural change:** the two right-aligned segments (watching, scan) are grouped into a new `.ws-status-right` wrapper (`display: flex; align-items: center; gap: 16px` — reuses the exact gap value `.ws-status-left` already uses) so the status bar's `justify-content: space-between` continues to work with exactly two top-level children (left group, right group) regardless of which conditional segments are present inside the right one. DOM order inside the group: **watching, then scan** — watching is the ambient/persistent state and sits closer to center; scan is the transient/urgent one and keeps the outermost, most-attention-grabbing position it already occupies today.

**Visibility:** rendered when `state.settings.watchDirectory` is true AND `state.catalogDir` is set (watching nothing is not a state worth announcing) — **omitted entirely when either is false**, the same "no reserved empty slot" rule the scan segment already follows. This is an optimistic display tied directly to the setting, not a confirmed "watcher is actually alive" signal threaded back from Go — `27-CONTEXT.md`'s Integration Points name only a bare `catalogs:changed` event with no payload, no watcher-health channel. See UI Considerations E4/error for why this is the deliberate resolution, not a gap.

**Markup and style** — a `<span>`, not a `<button>` (unlike the scan segment, there is no click destination; watching has no panel to reopen):

```
<span class="ws-status-watching">
  <span aria-hidden="true">●</span>
  <span>watching</span>
  <span class="ws-status-watching-dir">{catalogDir}</span>
</span>
```

- Inherits `mono` from the status bar's existing `.ws-status mono` class (correct anyway — the directory value is a path).
- `display: inline-flex; align-items: center; gap: 4px` (reuses the scan segment's exact gap value).
- Color: **`var(--fn)`, not `var(--ac)`** — a deliberate divergence from the scan segment's accent color. Scan is an active, urgent, clickable task; watching is passive background chrome the user should be able to ignore most of the time. Coloring both the same way would make two structurally different kinds of status compete for the same visual weight — reusing this app's existing tertiary-text token (already used for "0 catalogs"-style muted status-bar text) keeps watching legible but quiet.
- Directory value: `max-width: 160px; overflow: hidden; text-overflow: ellipsis; white-space: nowrap` — reuses the exact `160px` value already declared for `.ws-status-scan-name`, not a new number.
- No `title` attribute for the full untruncated path on hover. This app has never used that affordance anywhere else (not even on the scan segment's own name, which can truncate the same way) — adding it here only would be a one-off inconsistency, not a genuine gap.
- No `aria-live` region. A screen reader re-announcing this segment every time an external file changes debounces in from the watcher would be noisy and was never requested — plain, non-live text is correct here, matching the scan segment's own lack of `aria-live`.
