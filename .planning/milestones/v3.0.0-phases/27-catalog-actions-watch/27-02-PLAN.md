<recorded_decision id="parent-directory-fsync">
`27-CONTEXT.md` puts this in Claude's Discretion but requires it be **decided explicitly and recorded, not silently included or omitted**. `27-RESEARCH.md` rates its own supporting evidence MEDIUM confidence (corroborated web research, not a single canonical spec citation).

**Decision: ADD the parent-directory fsync**, with a deliberately non-fatal error path.

Reasoning, on the merits rather than by deferring to the recommendation:
- `tmp.Sync()` (the locked half) makes the *temp file's own bytes* durable. `os.Rename` then makes the swap atomic *within the running kernel's view*. Neither one flushes the directory entry that binds the destination name to the new inode — on POSIX that is a separate durability domain.
- The gap matters most in exactly the case ACT-09 names. `WriteFileAtomic` is a **replace**, not just a create: a power loss after a successful `os.Rename` but before the directory entry reaches stable storage can leave the destination name pointing at neither the old nor the new inode. For a catalog the user already had, that is the "existing catalog corrupted" outcome, not merely "the new write was lost."
- Cost is ~8 lines and one extra syscall per write. `WriteFileAtomic` runs a handful of times per catalog operation, never in a hot loop.
- The known platform divergence is handled rather than assumed away: Windows does not expose a directory handle you can `Sync()` the same way, so a `Sync()` error on the directory handle is logged-and-ignored, never propagated. The file's own `tmp.Sync()` still stands there, and `MoveFileEx`'s Windows semantics differ from POSIX rename durability anyway.
- **Hard constraint on the failure path:** a failed directory sync must NOT remove the destination file and must NOT return an error. The rename already succeeded; treating a best-effort durability hint as a fatal error would destroy a write that actually landed.

The Windows non-support is logged as a `.planning/WINDOWS.md` entry by plan `27-07`, alongside this phase's other platform-gated items — this project's standing convention is to track unverified/divergent platform behavior rather than claim parity.
</recorded_decision>

  <action>
Change `WriteFileAtomic` in `internal/catalog/atomicwrite.go` in exactly two places, leaving its signature, its temp-file-in-destination-directory rule, its `perm` handling, and every existing failure path intact.

**1. Flush the temp file's bytes before closing it.** Between the successful `tmp.Write(data)` and the `tmp.Close()` call, insert a `tmp.Sync()` step. On failure, use the same handling every other step already uses: close the handle, remove the temp path, return the error. This is `27-CONTEXT.md`'s locked half of ACT-09 — `os.Rename`'s atomicity says nothing about whether the temp file's bytes ever reached stable storage.

**2. Fsync the destination's parent directory after the rename succeeds.** Add an unexported helper `syncDir(dir string) error` that opens `dir` with `os.Open`, calls `.Sync()` on the returned handle, closes it, and returns the first error encountered. Call it immediately after a successful `os.Rename(tmpPath, path)` with `filepath.Dir(path)`, and **do not propagate its error** — the write still succeeds.

The non-propagation is load-bearing and must be commented as such: the rename has already succeeded and the file's own bytes are already durable, so a directory-sync failure is a weaker-durability outcome, never a failed write. Windows in particular does not expose a directory handle that can be synced this way, and propagating that platform's error would make every single write on Windows fail. Do **not** remove the destination file on this path, and do **not** return an error from it.

**But do not discard the error silently.** A directory sync that fails persistently — on some filesystem or platform — would leave exactly the durability hole this fsync was added to close, while every write still reports success: permanently unobservable. So capture the error into a named variable rather than the blank identifier, and on non-nil call `log.Printf` once with a message naming the directory and the error (the same `log` package `main.go` already uses; no new logging dependency, no new abstraction). One line. The comment above it should state that this is deliberately log-and-continue, not a swallowed check.

Update the function's doc comment to state the full four-step durability contract in order — temp file in the destination's own directory, `Sync()` the temp file's bytes, `Rename` for atomic replacement, best-effort parent-directory `Sync()` for the directory entry — and to record that the parent-directory step is best-effort by design because it is not supported uniformly across platforms. Reference `27-CONTEXT.md`'s discretion item and this plan's `<recorded_decision id="parent-directory-fsync">`.

Do not change `os.Chmod`'s position or the `0600`-to-`perm` explanation, and do not touch any caller.

Build the repo's first subprocess crash test. This is genuinely new work with no in-repo analog — design it, do not transcribe it.

**1. `internal/catalog/testdata/killtarget/main.go` — a standalone `package main` helper.**

It lives under `testdata/` so `go build ./...` and `go vet ./...` skip it (the Go toolchain ignores `testdata` directories), which is what keeps a deliberately-slowed write out of the production binary.

CLI contract, read from `os.Args`: a destination path, a payload byte count, and a delay in milliseconds. Behavior:
- Reproduce `WriteFileAtomic`'s sequence *locally, in this file* — `os.CreateTemp(dir, "storcat-*.tmp")` with the same name pattern, write the payload in two halves with the requested delay between them, `Sync()`, `Close()`, `Chmod`, `Rename`. It must not import `internal/catalog` and must not call the real `WriteFileAtomic`: the artificial mid-write delay is a test-only variant and must never be added to production code.
- The delay is what makes the kill schedulable at all. The real temp-then-rename window for a small catalog JSON is a few milliseconds; widening it to a controllable interval is the entire point of the helper.
- **Synchronization, not polling-on-hope.** After the first half of the payload is written and before the delay, write a zero-byte marker file at `<dest>.killtarget-ready` and `Sync()` it. The parent test waits for that marker rather than racing the temp file's mere appearance — `27-RESEARCH.md`'s Assumption A3 flags polling for the temp file as the part of the design most likely to prove unreliable, and names an explicit marker as the fallback. Build the marker in from the start; it is three lines and removes the flakiest variable.
- Exit 0 if it somehow completes without being killed (the parent treats that as an inconclusive iteration, not a pass).

**2. `internal/catalog/atomicwrite_sigkill_test.go` — `TestWriteFileAtomic_SurvivesKill`.**

- `t.TempDir()` for both the build output and the write destination.
- Build the helper once per test run with `exec.Command("go", "build", "-o", <tmpBin>, "./testdata/killtarget")`; a build failure is `t.Fatal`. Guard the whole test with `if testing.Short() { t.Skip(...) }` so `-short` runs stay fast.
- Seed the destination with known "previous catalog" content — a valid, distinctive JSON payload — and record its exact bytes and its SHA-256.
- Loop **at least 20 iterations**, varying the injected delay across the range (e.g. 20ms, 50ms, 120ms) so the kill lands at different points in the window rather than proving one timing. Per iteration:
  1. `exec.Command(tmpBin, dest, payloadSize, delayMs)`, `Start()`.
  2. Wait for the `<dest>.killtarget-ready` marker with a short bounded poll (a `time.Ticker` plus a hard deadline; a missed marker is `t.Fatal`, never a silent skip — a test that quietly stops proving anything is worse than a red one).
  3. `cmd.Process.Kill()` — this sends `SIGKILL` on Unix. That is the actual mechanism; do not substitute `Signal(os.Interrupt)`, and do not use an in-process `panic`/`os.Exit`, which exercise Go's deferred cleanup rather than a violent process end.
  4. `cmd.Wait()` and assert the process really died from a signal rather than exiting normally.
  5. **Assert the destination is byte-identical to the seeded content** — same length, same SHA-256. This is ACT-09's actual claim: a crash mid-write cannot corrupt an existing catalog.
  6. Assert the destination still parses as JSON (a truncated write would not).
  7. Clean up any `storcat-*.tmp` and the marker before the next iteration, and record how many were left behind. Temp residue after a SIGKILL is *expected* — the killed process never reaches its own `os.Remove` — so this is reported in the summary, not asserted to be zero. What must be zero is residue at the *destination path itself*.
- Add `TestWriteFileAtomic_SurvivesKill_NoPriorFile` as a second case: the same loop with no pre-existing destination. After each kill the destination must be **absent** — never present-but-truncated. A reader must never find a half-written catalog where none existed.
- Set a generous `-timeout`-friendly budget; keep total wall clock under ~45s so the suite stays usable.

**3. If the harness proves unreliable, say so.** If, after honest iteration, the kill cannot be landed inside the window reliably enough for the assertions to mean anything, do **not** weaken the assertions until it goes green. Commit what was built, mark the test `t.Skip` with the concrete reason, and record in the SUMMARY that `.planning/WINDOWS.md` #6 stays open. Plan `27-07` reads this SUMMARY to decide whether to mark #6 fixed; a false "fixed" is worse than an honest open item, and this exact ledger entry exists because a prior phase declined to fake it.
