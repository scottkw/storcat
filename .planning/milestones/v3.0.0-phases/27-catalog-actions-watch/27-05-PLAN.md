Create the dialog. It is **always mounted** by its parent and gated by `isOpen` through `DialogShell`, the same shape `RenameDialog` uses — the shared hook must observe the `true → false` transition to release the scroll lock and restore focus.

**Props:** `isOpen: boolean`, `onClose: () => void`, `catalog: models.CatalogMetadata`, `catalogDir: string | null`, `onDeleted: () => void`.

**State:** `deleteHtml: boolean`, `busy: boolean`, `error: string | null`. Re-seed all three in an `isOpen`-keyed effect — `deleteHtml` back to `true`, `busy` to false, `error` to null — for the same reason `RenameDialog` does: an always-mounted component's `useState` initializer runs once at app start and would carry a previous catalog's state into the next open.

**Derived values.**
- `htmlPath` = the catalog's `.json` path with a trailing `.json` replaced by `.html`. This mirrors the same-directory/same-basename convention already implemented identically in `internal/search/service.go` and `app.go`; it is used for **display only**. The path actually deleted is derived independently in Go by `App.DeleteCatalog`, which never accepts an HTML path from the renderer — so a mismatch here could mislead the user but could never cause a different file to be deleted.
- `showHtmlRow` = `catalog.hasHtml`.
- The primary label = `Move both to Trash` when `catalog.hasHtml && deleteHtml`, otherwise `Move to Trash`. Resolve it as an explicit two-branch expression; there is no third state.

**Confirm body**, in a `.ws-dialog-body` (the shell supplies the 20px padding and the 16px column gap):
1. `<p className="ws-delete-lead">` with the exact string `This moves the file(s) below to the Trash — you can restore them from the Trash until it's emptied.` This copy is load-bearing: it is the only place in the dialog that tells the user the action is recoverable, which is precisely why `REQUIREMENTS.md`'s Out of Scope table rejects a type-to-confirm gate as disproportionate. Do not reword or shorten it.
2. A `.ws-delete-row` with a `.ws-delete-path-label` reading `Catalog (.json)` above a `.ws-delete-path-box mono` containing `catalog.path` verbatim and in full. Never ellipsize, never truncate, never add a `title` attribute in place of showing the path.
3. When `showHtmlRow`, a second `.ws-delete-row` with the label `HTML (.html)` and the derived `htmlPath` in the same box treatment. When `showHtmlRow` is false this row is **omitted entirely** — not rendered disabled, not greyed — matching this app's established convention that a row whose only possible outcome is inapplicable should not exist.
4. When `showHtmlRow`, a `<label className="ws-delete-check">` wrapping a native `<input type="checkbox">` bound to `deleteHtml` and the text `Also delete the matching .html`. **Checked by default** — the `.json`/`.html` pair is what a user thinks of as "the catalog", and leaving an orphaned HTML behind is the surprising outcome. The checkbox row renders only alongside path box 2.

**Error sub-state.** Same mounted dialog, body and footer swapped — never a second dialog. Keep the lead sentence, both path boxes and the checkbox visible above the error so the user retains the context of what was being deleted. Below them render `<div className="ws-dialog-error">` with `Couldn't move ` + `catalog.title` + ` to the Trash: ` + the returned error + `.`. The literal OS/`wastebasket` error surfaces; do not substitute a generic string, do not prefix it with reassurance, and do not truncate it.

**Footers.**
- Confirm: secondary `.ws-dialog-btn` reading `Keep catalog` (calls `onClose`), then primary `.ws-dialog-btn ws-dialog-btn-danger` with the resolved label above.
- Error: secondary `.ws-dialog-btn` reading `Keep catalog` (unchanged — closes with nothing deleted), then primary `.ws-dialog-btn ws-dialog-btn-danger` reading `Try moving to Trash again`.
- **There is no third button in either footer, no delete-permanently link anywhere in the component, and no wording in any string that implies a fallback exists.** This is ACT-05's explicit, non-negotiable requirement and it governs every word in this file, not just the primary action.
- While `busy`, both buttons carry `disabled` and the primary carries `opacity: 0.7`, reusing `DetailsPanel`'s Footer treatment verbatim. No spinner — this project has no spinners.

**Submit / retry — one handler, called by both primaries.** Guard on `busy`. If `catalogDir` is null, set `error` to `No catalog directory configured.` and stop, failing closed exactly as `RenameDialog` and `Footer` already do. Otherwise set `busy`, call `wailsAPI.deleteCatalog(catalog.path, catalogDir, deleteHtml)`. On success call `onDeleted()` then `onClose()`. On failure set `error` from the returned message and clear `busy`.

Retry re-invokes with the **same path and the same checkbox state** and needs no bookkeeping about what already succeeded: `27-03`'s `osutil.TrashPaths` skips a path that is no longer on disk, and `27-RESEARCH.md` verified every `wastebasket` backend does the same internally, so a retry after a partial failure re-attempts only what remains. Do not build a diff of what changed — that is unnecessary complexity the backend's idempotency already covers.

`initialFocusRef` should point at the secondary `Keep catalog` button, so the destructive action is never the element under an accidental Enter on open.
