# Phase 23 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Source of truth:** `design_handoff_storcat_ui/README.md` §"Screens / views → 1. Workspace" + §"Interactions & behavior" + §"State management", and the literal markup in `design_handoff_storcat_ui/designs/StorCat 1a Demo.dc.html` (lines 100–239 for rail/tree/details/status-bar markup, 852–1120 for the row/color/copy logic). Per REQUIREMENTS.md: "where this document and the handoff disagree, the handoff wins."
>
> **This phase fills Phase 22's skeletons with real data.** All tokens, type scale, spacing, radii, shadows, density tokens (`--rh/--rp/--mp/--hp/--fs`), z-index scale, and icon contract are locked in `22-UI-SPEC.md` — this document does not restate or renegotiate them. It only specifies what changes when the rail, tree, details panel and status bar go from unconditional-empty to data-driven, plus three new surfaces the prototype introduces here: populated rail rows, populated tree rows with virtualization, the catalog header + breadcrumb, and the unreadable-catalog (STATE-02) panel.

## Rail Contract (RAIL-01–06)

Row markup (per catalog, `padding: var(--rp)`, `border-radius: 6px`, `gap: 1px` between rows — all from `22-UI-SPEC.md`'s scale):

- **Line 1:** 6px status dot (`display:block`, `border-radius:50%`, `background: #e5534b` when `catalog.parseError` is non-empty, else `transparent` — never removed from the DOM, so row heights stay identical whether or not a catalog is broken) · title (12.5px/500, ellipsized, `flex:1`) · JSON size (10.5px mono `--fn`, `flex:none`).
- **Line 2:** `{filename} · {fileCount} files` — 10.5px mono `--fn`, `white-space: nowrap`. Always plural "files" (no singular special-case — matches the "0 files indexed" status-bar precedent from Phase 22; do not add grammatical branching for `fileCount === 1`).
- **Selected state:** `--sel` background, 2px `--ac` left border, title in `--ac`. **Hover:** `--hov` background (rows are otherwise transparent).
- **Click behavior (RAIL-03):** sets current catalog, clears `selected` (node selection), expands the tree root — one atomic reducer action per `23-CONTEXT.md`.

**Header count** (`"CATALOGS {n}"`) always shows the **total** number of catalogs in the directory, never the filtered subset — confirmed against the prototype's own logic (`catalogCount: s.catalogs.length`, computed independently of `railFilter`).

**Filtering (RAIL-02):** case-insensitive substring match against `title + filename` combined, run in the rail component's local state via `useDeferredValue`. **Zero-match state** (not shown in the handoff — genuinely new this phase): render a single centered line, 11.5px `var(--dm)`, in the same scroll region the rows would occupy: `No catalogs match "{filter}".` — deliberately a one-line notice, not the full STATE-01 empty-library block (heading + body + link), since this is "no matches for a search," not "no catalogs exist."

**Red status dot (RAIL-04):** driven by `CatalogMetadata.parseError !== ''`. The row stays clickable and selectable when broken — selecting it routes to the unreadable-catalog panel (see below), not a disabled state.

**Directory chip (RAIL-05) — now interactive, superseding Phase 22's "non-interactive this phase" note:**
Phase 26 owns the full Settings surface, but `RAIL-05` itself ("sees the current catalog directory as a chip... and can change it") is scoped to Phase 23 in the requirements traceability table, and the backend capability it needs (`SelectDirectory`) already exists (listed as a Phase 22 "Reusable Asset"). Resolution: clicking the chip opens the native folder picker via the existing `SelectDirectory` binding; on selection, persist the path (a new localStorage key following the established `storcat-*` convention, e.g. `storcat-catalog-directory`) and re-run `BrowseCatalogs` against it. Visual footprint is unchanged from Phase 22 (11px mono, `--ch` fill, 1px `--l` border, ellipsized) — only the `cursor: pointer` and a `--ac` hover border are added, matching the search-field hover convention. No directory-diffing, no "recent directories" list, no validation UI beyond what `SelectDirectory`'s native dialog already provides — that scope stays with Settings (Phase 26).

**First-run / no directory set:** if no persisted directory exists yet, do not call `BrowseCatalogs` at all — render the same STATE-01 empty-library treatment (rail block + tree-pane empty state) as the zero-catalogs case. This avoids inventing a fourth state; the directory chip (now clickable) is the way out of it.

**"＋ New" pill (RAIL-06):** stays inert this phase — its target, the create slide-over, is Phase 25. This is unchanged from Phase 22; do not wire it to a stub.

## Tree Pane Contract (TREE-01–08)

### Catalog header (TREE-04)
`padding: 14px 18px 12px`, 1px bottom border `--l`:
- Title: 17px/600, `letter-spacing: -0.01em`.
- Two mono chips (`{filename}.json`, `{filename}.html`): 11px, `--ch` fill, `border-radius: 5px`, `padding: 2px 7px`.
- Metadata line: 11.5px mono `--dm`, four values joined by `|` dividers in `--l`: `{fileCount} files | {jsonSize} | {totalBytes formatted} catalogued | modified {date}`.

**"HTML" chip when no HTML exists:** the handoff always shows both chips (every demo catalog has both files). If a catalog has no matching `.html` (write-HTML was ever toggled off — a Phase 25 concept, but real v1/v2 catalogs can already lack one), omit the `.html` chip entirely rather than rendering a disabled/greyed one — matches the general contract of "don't show controls for capabilities that don't apply," and avoids inventing a new visual state for something the handoff never designed.

### Breadcrumb bar (TREE-03, TREE-05)
34px, `--p2` background, 1px bottom border `--l`:
- Path text, mono, format `/ {CATALOG_ID} / {ancestor} / {ancestor} / {current}` — **ancestor segments in `--ac`, the final (current) segment in `--tx`.** The prototype's own markup renders this as a single flat string in one span with no distinct coloring (a limitation of its minimal templating engine, not a design decision) — but `TREE-05` is an explicit requirement ("ancestor segments in the accent color"), so the real implementation must render each `/ segment` as its own `<span>` with per-segment color, not one flat string. This is the one place this UI-SPEC diverges from the prototype's literal markup in favor of the written requirement.
- Breadcrumb segments are **not individually clickable** — only the whole-bar "Expand all" / "Collapse" links are interactive (no per-segment `onClick` exists anywhere in the prototype's logic; `23-CONTEXT.md`'s "breadcrumb interaction details beyond the specified collapse-to-root" discretion is resolved as: none — segments are display-only).
- **Long-path overflow (not covered by the handoff — resolved here):** the text container gets `flex: 1 1 auto; min-width: 0; overflow: hidden; text-overflow: ellipsis; white-space: nowrap`, with the two action links `flex-shrink: 0`, so a deeply-nested selection truncates the path rather than pushing "Expand all"/"Collapse" off the bar.
- "Expand all" (`--ac`, TREE-03): expands every directory node in the current catalog. "Collapse" (`--dm`, hover `--ac`): collapses to root only (keeps the root's own children hidden, matching the prototype's `collapseAll` which re-opens only the synthetic root index).

### Tree rows (TREE-01, TREE-02, TREE-06)
Fixed height `var(--rh)` (27/34px), `padding-left: 18px + depth * 16px`, `padding-right: 18px`, `gap: 8px`:
- Caret: 10px mono `--fn` — `▾` when an expandable directory is open, `▸` when closed, empty for files and for directories with no children.
- Shape: 9px, `border-radius: 2px` + `--ac` fill for directories, `border-radius: 50%` + `--fn` fill for files.
- Name: mono, `var(--fs)`, ellipsized, `--ac` when selected else `--tx`.
- Size: right-aligned, 11px mono `--fn`, `flex: none; white-space: nowrap`.
- Row background: `--sel` when selected, `--hov` on hover, else transparent.
- **Click (TREE-02):** directory click toggles expand *and* selects; file click selects only.
- **No per-folder "show N more" overflow row.** The prototype's `__more__`/"show 12 more" affordance (demo lines 664–901) is a sketch the handoff's own README calls out explicitly as scope: *"this is the one place the prototype is a sketch... virtualize the full list."* `23-CONTEXT.md` locks full flattening + `@tanstack/react-virtual` windowing instead — every node in the flat array is reachable by scrolling, none are capped or hidden behind a "show more" row. Do not port the `__more__` row type.

### Virtualization / scale gate (TREE-01)
- Fixed row height from `--rh`, no dynamic measurement (locked).
- 40,000+-node fixture must scroll smoothly with no freeze — this is a functional/performance gate, not a visual one; overscan row count is an implementation detail left to the executor (a small buffer, e.g. 8–12 rows, is typical for `@tanstack/react-virtual` and is not a contract requirement here).
- Depth is unbounded by this contract (no max-depth indent cap) — matches the handoff exactly. Real catalogs rarely nest deep enough for `18 + depth×16` to consume the row's width; this is a known, accepted limitation, not something to engineer around this phase.

### Selection reset on catalog switch (TREE-06)
One atomic action clears `expanded`, clears `selected`, resets scroll to 0 — already locked in `23-CONTEXT.md`; recorded here because it directly affects visible state (a stale scroll position or leftover expansion is a visual bug, not just a state bug).

## Details Panel Contract (TREE-07, TREE-08)

Two states, both reachable this phase (the "nothing selected" state from Phase 22 remains when `currentCatalogId` is null):

**Catalog-level (no node selected — the default after selecting a rail row):**
- Heading: "Catalog" (12px/600 uppercase `--dm`).
- Name: catalog title, 12.5px mono. Path: `{catalogDirectory}/{filename}.json`, 11px mono `--dm`.
- Meta rows: `Files` / `Catalogued` / `JSON` / `Modified` — **no "HTML" row.** The prototype's fifth row hardcodes `HTML: present`, which would require a new existence-check backend capability outside `23-CONTEXT.md`'s locked "exactly three backend surfaces." The `.json`/`.html` chips in the tree header already communicate the HTML file's existence (or its absence, per the header rule above) — dropping this row avoids duplicating that signal and avoids inventing backend work.

**Node-level (a file or directory selected in the tree):**
- Heading: "Selected file" or "Selected folder" (dynamic on node kind).
- Name (mono, `word-break: break-all`) + full path (mono, `--dm`).
- Meta rows: `Type` / `Size` / `Catalog` / `Depth` / `Indexed` (catalog's modified date) — all 11.5px, label `--dm` left, value mono right, `padding: var(--mp) 0`, `border-bottom: 1px solid var(--l2)`.

**`⋯` button:** renders structurally (22px, 1px `--l` border, `border-radius: 6px`, hover `--ac`) in both states, matching the handoff's header row — but stays **inert** this phase (click is a no-op, no menu opens). The actions menu it opens (rename/duplicate/delete/re-scan) is `ACT-01`, Phase 27. This is the same "render but don't wire" convention Phase 22 established for the "+ New" pill.

It is icon-only, so it carries `aria-label="Catalog actions"` **now**, with the glyph marked `aria-hidden="true"`. Phase 22's UI-SPEC established that every control whose entire label is an icon carries an explicit accessible name; an inert button is still focusable and still announced, so the name is not something to retrofit in Phase 27. `aria-haspopup="menu"` and `aria-expanded` are deliberately NOT set this phase — there is no menu yet, and claiming one would be a lie to assistive tech. They land with the menu in Phase 27.

**Footer — exactly two buttons this phase (TREE-08), not the handoff's three:**
1. **"Open HTML catalog"** — primary, `--ac` fill / `--onac` text, 30px tall, `border-radius: 7px`. Reuses the existing `GetCatalogHtmlPath` + `OpenExternal`/`ReadHtmlFile` bindings (Phase 22 CONTEXT's reusable-assets list).
2. **Reveal-in-file-manager** — outlined (1px `--l`, hover `--ac` border). Label is **platform-aware**, mirroring `RevealInFileManager`'s own per-OS behavior locked in `23-CONTEXT.md`: "Reveal JSON in Finder" (macOS), "Reveal JSON in Explorer" (Windows), "Reveal JSON in file manager" (Linux) — determined from the same platform check the Go binding already needs, not hardcoded to the handoff's macOS-only "Finder" copy.

The handoff's third button, **"Re-scan volume…"**, is omitted entirely this phase — it belongs to `ACT-06`/`ACT-08` (Phase 28) and there is no backend surface for it in `23-CONTEXT.md`'s locked three additions. Do not render it inert; two buttons, not three.

## Unreadable-Catalog Panel (STATE-02) — replaces the tree pane, not a modal or toast

Triggered when the selected rail catalog's `parseError` is non-empty. `padding: 24px 22px`, `flex-direction: column`, `gap: 18px`:

- **Badge + heading:** 22px `!` badge (`rgba(229,83,75,.16)` fill, `#e5534b` text, `border-radius: 6px`) + "This catalog can't be read" (15px/600).
- **Explanation paragraph** (12.5px, `--dm`, `max-width: 520px`, `line-height: 1.6`): kept **generic**, not scenario-specific like the handoff's "probably written while the card was pulled" prose (Go's JSON errors don't reliably classify truncation vs. malformed syntax vs. encoding). Fixed copy: *"This catalog's JSON couldn't be parsed. The .html copy may still open, and the volume can be re-scanned later to rebuild it."*
- **Meta rows** (11.5px, `border-bottom: 1px solid var(--l2)`, `max-width: 520px`): `File` (filename) / `Failed at` (`byte {offset}`, from `json.SyntaxError.Offset`) / `Reason` (short parser-supplied description) / `Parser` (which format was attempted — e.g. `"v2 object / v1 array"`, reflecting `LoadCatalogFlat`'s reuse of `LoadCatalog`'s dual-format parse).
- **Raw error box:** `--ch` fill, `border-radius: 9px`, `padding: 12px`, 11.5px mono, `#e5534b`, `word-break: break-all` — the verbatim parser error string, unedited.
- **No action buttons this phase.** The handoff's three recovery actions ("Re-scan volume", "Open the .html instead", "Remove from library") are `STATE-03`, explicitly mapped to **Phase 28** in `REQUIREMENTS.md`'s traceability table — not Phase 23. Rendering one or two of the three inert while the rest wait for later phases would be an asymmetric, confusing partial affordance; omit all three. The task's own critical-context brief ("must show filename, byte offset, reason and the raw parser error") independently confirms the diagnostic content is the whole of this phase's scope.
- **Rail row:** keeps its red status dot (RAIL-04) and stays selectable — selecting it again just re-renders this same panel.

While the load is in flight the tree pane owns the loading surface (see E7); the header area stays empty rather than showing a skeleton that would shift layout when real values arrive. |
| error | ✅ explicit | On a parse failure the header is not rendered at all; the unreadable-catalog panel replaces the whole tree pane including this bar. There is no half-header showing a title for a catalog that could not be read. |
| overflow | ✅ explicit | Title ellipsizes on one line (`white-space: nowrap; overflow: hidden; text-overflow: ellipsis`). The breadcrumb bar scrolls horizontally within its own `overflow-x: auto` container and never wraps to a second line or widens the tree pane — a deep path must not change the grid. |
| long-text | ✅ explicit | Breadcrumb segments are per-segment spans (not one string), so a single very long directory name ellipsizes within its own segment while the ancestors stay readable and clickable. The metadata line's numbers are formatter-bounded by construction. |

### E5 — Status bar, live counts (static-content)

| Category | Status | Resolution |
|----------|--------|------------|
| overflow | ✅ explicit | Fixed 26px height, never wraps, never scrolls; segments are `flex-shrink: 0`. Counts that grow into the millions must not push a segment off the bar — the formatter abbreviates (e.g. `1.2M files indexed`) rather than letting the strip overflow. |
| long-text | ✅ explicit | All three segments are formatter output (`fmt`/`gb` from the handoff), so their width is bounded by the formatter, not by user data. No catalog title or path ever appears in the status bar. |

### E7 — Catalog load data path: `LoadCatalogFlat` + sidecar count cache (list-collection / static-content)

| Category | Status | Resolution |
|----------|--------|------------|
| empty | ✅ explicit | A catalog whose root has zero contents parses successfully and yields a flat array of length 0. The tree pane renders its own "this catalog is empty" state — NOT the empty-library state (which means "no catalogs in the directory") and NOT the unreadable state (nothing failed). These three empties are visually distinct and must not be collapsed into one component. |
| loading | ✅ explicit | Parsing 40,000 nodes is measurably slow, so the tree pane shows a loading state while `LoadCatalogFlat` is in flight. Per the handoff's "no spinners — progress is always a real number" rule this is a quiet state, not a spinner. The rail stays fully interactive during the load; selecting a different catalog mid-load is allowed and must supersede. |
| error | ✅ explicit | Every failure mode surfaces in the unreadable-catalog panel with its real cause, never a generic message: file missing (deleted between listing and load), permission denied, truncated JSON, malformed JSON, and a valid JSON document that is not a catalog. The raw parser error is shown verbatim with its byte offset. |
| populated | ✅ explicit | The flat array's `depth` and `hasChildren` fields fully determine rendering — the frontend never re-derives hierarchy by re-walking. Row count at 40,000 nodes must not change the DOM node count: the virtualizer's rendered row count stays proportional to viewport height, not to array length. This is the phase's core performance contract and is directly measurable. |
| partial | ✅ explicit | A catalog that parses but contains entries the original scan skipped (permission-denied directories, broken symlinks) loads normally — those entries simply are not present. The tree does not fabricate placeholder rows for them, and their absence is not an error state. |
| overflow | ✅ explicit | The flat array is held once in memory and sliced for display; it is never copied per render. A catalog large enough to be slow to parse must still not be re-flattened, re-sorted or re-filtered on every keystroke or scroll frame — the `expanded` Set drives an index computation, not an array rebuild. |
| zero-one-many | ✅ explicit | Zero nodes → the empty-catalog state above. One node (a root with no children) → renders as a single row with no caret, not as an error or an empty state. Many (40,000+) → the virtualization contract. All three are distinct and all three must be exercised. |
| long-text | 🧪 backstop | A pathologically long single filename or a very deep path (hundreds of levels) ellipsizes per row and indents to a capped maximum rather than pushing the row's size column out of the pane. Verified by observation against a generated fixture rather than by a specific length-boundary assertion. |
