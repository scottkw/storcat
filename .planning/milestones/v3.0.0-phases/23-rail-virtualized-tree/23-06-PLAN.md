<objective>
Make the details panel follow the selection and give it its two working actions — open the catalog's HTML copy, and reveal its file in the operating system's own file manager — with the process-spawning half built so that no character in a filename can ever become a command.

Purpose: this is the phase's only new operating-system integration and its highest-severity security surface. It is also small enough that getting it exactly right costs almost nothing, which is precisely why there is no excuse for a shell string.
Output: a validated, argv-only reveal binding with all three platform shapes under test, and a details panel that tracks the selection with a two-button footer.
</objective>

  <action>
Create package `osutil` at `internal/osutil/reveal.go`. Deliberately do not use build tags or per-platform source files: define three pure builders, one per platform, each taking the resolved absolute path and returning a command name and an argument slice, plus one switch on the current platform that selects among them. `23-RESEARCH.md` sketches three build-tagged files; a single untagged file with pure builders is the same behaviour and lets all three shapes be tested on this macOS development machine instead of only the one the compiler selects — that testability is worth more here than mirroring the sketch.

The macOS builder returns the system open utility with the reveal switch and the path as two separate arguments. The Windows builder returns the file explorer with a single argument formed by joining the select switch and the path with no space, which is the shape community precedent uses and which `23-RESEARCH.md` flags as its own unverified assumption. The Linux builder returns the desktop open utility with the path's parent directory as its only argument, because no universal select-this-file mechanism exists across Linux file managers. An unrecognised platform returns an empty command name.

`RevealInFileManager(path string) error` resolves the path to an absolute cleaned form, resolves symbolic links so a link cannot point the reveal at something outside the catalog directory, and then rejects anything that is not an existing regular file whose extension is the catalog extension or the HTML extension. Only after all of that does it build the argument vector and run the command. The path is always a distinct element of that vector and is never joined into a command line or handed to an interpreter of any kind; this is the entire mitigation for the phase's highest-severity threat, and the standard library's process API bypasses the shell completely when used this way. Wrap every failure with the file path and the underlying error using the standard wrapping verb, following the error style already used in `app.go`.

Write `internal/osutil/reveal_test.go` covering every line of the behavior block as table tests. The hostile-path case is the important one: assert the exact element count and the exact element contents rather than a substring match, so an accidental split or an accidental join both fail. The rejection cases must assert the error without any process being spawned, which follows naturally from validating before building the vector.

Then add `func (a *App) RevealInFileManager(path string) error` to `app.go`, delegating to the package, and regenerate the bridge with `wails generate module`. Add a `revealInFileManager` wrapper to `wailsAPI.ts` following the existing envelope shape character for character. Never hand-edit anything under `frontend/wailsjs`.
