### RAIL-06 — traceability corrected during this audit

RAIL-06 ("user can open the create slide-over from the ＋ New pill") was recorded `Pending`.
Phase 23 deliberately left the pill inert because its target slide-over did not exist until
Phase 25, and both `23-CONTEXT.md` and `23-UI-SPEC.md` explicitly forbade wiring it to a stub.
Phase 25 built the slide-over and wired the pill, but nobody updated the traceability.

Verified in code, not inferred: `CatalogRail.tsx:151` carries `onClick={openCreatePanel}`, and
the integration checker traced the full path `openCreatePanel()` → `SET_CREATE_OPEN` →
`WorkspaceShell` → `CreateSlideOver`. Traceability updated to Complete. This was stale
bookkeeping, never a functional gap.

### COMPAT-06 — deliberately partial, not a gap

COMPAT-06 reads "the app builds, signs, notarizes, and releases on all existing CI platform
targets." Phase 28-06 proved the **build** leg with a real green Actions run and then refused to
claim the rest:

- Run: https://github.com/scottkw/storcat/actions/runs/31976677486 (commit `2715a42d`)
- All three legs individually `success`: `build-macos`, `build-linux`, `build-windows`
- Independently confirmed at audit: exactly one `build.yml` run for that SHA, no `v3.0.0` tag on
  origin, `release.yml` not triggered by the push

**What that proves:** native compilation on all three real runner OSes, plus frontend TypeScript
type-checking (`frontend:build` runs `tsc` before `vite build`, so a type error fails the job).

**What it does not prove:** no signing, no notarization, no execution of any built binary. Those
live in `release.yml` behind a `v*.*.*` tag, and Windows signing is a skip-with-warning branch
while CRED-04/CRED-05 are unprovisioned.

Leaving this unchecked is the correct record. Marking it complete would put an unverified
assertion into the milestone archive at exactly the point a future reader would trust it most.

## Code Review Outcome (Phase 28)

Phase 28's review found 1 Critical and 3 Warnings, all fixed before completion:

- **CR-01** — `ComputeDiff` tested `!existed` before `newItem.Unreadable`, so a new-and-unreadable
  path was filed as `added` with a fabricated 0B size and its `ReadError` dropped. Reordered; the
  regression test was confirmed to fail against the old ordering and pass against the fix.
- **WR-01** — `ResolveRescan` cleared its retained tree before attempting the write, so any write
  failure lost it permanently — while the UI left all three buttons enabled inviting a retry that
  could never succeed. Now clears only after success, following `WritePartialCatalog`'s pattern.
- **WR-02** — `catalogDir` was taken from the frontend; now derived from config like `RescanCatalog`.
- **WR-03** — dead CSS rule removed.

## Accepted Deviations

Reviewed and accepted by the user during execution. Recorded so they are not mistaken for defects
or silently rediscovered later:

1. **Menu item not dimmed during concurrent scan** (28-03) — `Menu.tsx` deliberately unmodified;
   `MenuItemSpec` has no per-item `disabled`/`title`. The guard is functional: clicking during a
   scan surfaces the locked tooltip and never opens the dialog. The details-panel footer button
   does dim correctly.
2. **`ResolveRescan` takes a plain `string` mode** (28-04) — Wails codegen cannot emit a TS type for
   a defined string-const type in `internal/` used only as a parameter. `WriteRescanResult` keeps
   the typed `catalog.ResolveMode`.
3. **Keep-both label carries no filename** (28-04) — a predicted name is not collision-checked, so
   the label named a file it might not write. Dropped rather than lie.
4. **`ComputeDiff` prunes unreadable descendants** (28-02) — beyond the plan's literal text, and the
   phase's primary data-integrity control: without it a locked directory reports `unreadable` while
   every file beneath it reports `removed`, letting an overwrite destroy readable-tomorrow data.
