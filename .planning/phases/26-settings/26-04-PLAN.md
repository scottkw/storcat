  <action>
Create the pure validator FU-23-A needs, with no Wails runtime in reach so it is exercised directly by tests.

**`internal/osutil/openexternal.go` (new).** Add `ResolveContainedFileURL(raw string, catalogDir string) (string, error)`. It lives in `osutil` so it can reuse the package's existing `allowedRevealExtensions` map and `ContainsPath` helper directly — do not add a second containment function anywhere; `ContainsPath`'s own doc comment already records that it is the shared gate and explains why a `strings.HasPrefix` check would wrongly admit a name-prefix-sharing sibling directory. Validation order, each step failing closed with a wrapped error naming the input:
  1. reject an empty `catalogDir` up front, matching `RevealInFileManager`'s own "no catalog directory configured" precedent;
  2. derive a filesystem path from `raw` — when `raw` contains a scheme separator, parse it with `net/url` and require the scheme to be exactly `file` and the host to be empty or `localhost`, then take the parsed (percent-decoded) path through `filepath.FromSlash`; otherwise treat `raw` as a bare filesystem path, which is what the details panel passes today;
  3. require the derived path to be absolute — this is what rejects the scheme-less hostile inputs (`javascript:`, `data:`) as well as relative paths, without needing a scheme denylist to keep up with new schemes;
  4. `filepath.Abs` then `filepath.EvalSymlinks`, so a link cannot point the later checks at a different target than the one that gets opened;
  5. `os.Stat` the resolved path: it must exist and `Mode().IsRegular()` must be true (which also rejects directories and devices);
  6. the lowercased extension must be in the package's existing `allowedRevealExtensions` map;
  7. `ContainsPath(catalogDir, resolved)` must return true;
  8. return a canonical `file://` URL built from the resolved path with `net/url`'s `URL` type — returning the *resolved* path is what stops the caller re-introducing the symlink the validator just followed.
Carry a doc comment stating that this closes FU-23-A for `OpenExternal`, that restricting to `file://` inside the catalog directory was chosen over allow-listing URL schemes because the binding's only live caller opens a catalog's own HTML file, and — matching the honesty of `RevealInFileManager`'s existing note — that the EvalSymlinks-then-Stat-then-open sequence leaves the same accepted TOCTOU window, exploitable only by an attacker who already has local write access to the resolved path.

**`internal/osutil/openexternal_test.go` (new).** Write the table above using `t.Run` subtests and the `TestContainsPath` fixture pattern: build the catalog directory under `t.TempDir()`, canonicalise it with `filepath.EvalSymlinks` before constructing any expected value, and note in a comment that this is required because macOS's `t.TempDir()` lives under a symlinked `/var`.
  </action>
