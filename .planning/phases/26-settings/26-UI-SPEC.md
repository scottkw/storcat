## Dialog Shell, Entry Points & Overlay Coexistence (SET-01)

**Mount pattern:** `WorkspaceShell` always mounts a single `SettingsDialog` instance (same pattern as `CommandPalette`), receiving a parent-owned `isOpen` boolean gated in `AppContext` or local `WorkspaceShell` state — the same shape the palette already uses. **No animated exit** (unlike `CreateSlideOver`): the dialog mounts and unmounts on the `isOpen` boolean directly, matching the palette's model, not the slide-over's `closing`-flag model — nothing about Settings needs a visible exit animation to preserve (no in-flight scan, no unsaved draft).

**Scrim & panel:** `position: absolute; inset: 0; background: rgba(4,6,9,.62); display: flex; align-items: center; justify-content: center; z-index: var(--z-dialog)`. Click on the scrim (not the panel) closes the dialog — the panel stops click propagation, the same `onClick={{stop}}` convention every prior overlay in this app uses. Panel: `width: 660px; max-height: 700px; border-radius: 12px; background: var(--p); border: 1px solid var(--l); box-shadow: 0 30px 70px rgba(0,0,0,.6); display: flex; flex-direction: column; overflow: hidden`. Transition: **100ms scrim fade, no movement** — the same "Modals and the ⌘K palette" rule `24-UI-SPEC.md` already applied to the palette; a new `ws-settings-scrim-in` keyframe with identical 100ms values (kept as its own declaration per this project's one-keyframe-per-surface convention, `25-UI-SPEC.md`), not a shared class with the palette.

**Header (50px, 1px bottom border `--l`):** "Settings" (15px/600) + `⌘,` hint (11px mono `--fn`) + `×` (16px `--dm`, `margin-left: auto`, **`aria-label="Close"`** — the exact icon-only-control convention `22-UI-SPEC.md`'s Icons contract established and `25-UI-SPEC.md`'s create-slide-over header already reused).

**Footer (56px, `--p2` background, 1px top border `--l`):** left-aligned status line (11px mono `--fn`) `"StorCat 3.0.0 · settings save as you change them"` — verbatim from the handoff, and load-bearing copy: it is the only place in the dialog that tells the user there is nothing left to save — plus a right-aligned button. **This button's label diverges from the handoff's literal "Done"** — per this phase's explicit generic-label warning (Phase 25's UI-SPEC was blocked for a bare "Cancel"), "Done" used generically for a close-only action fails the same bar. Resolution: **"Close settings"** — 32px, `--ac` fill, `--onac` text, `border-radius: 8px`, `padding: 0 16px`, 12.5px/600, same visual treatment as the handoff's button, only the label changes. It closes the dialog exactly as `×`/Escape/scrim-click do — it is not a save action (there is nothing to save) and not a cancel action (there is nothing to discard).

**All four close paths (Escape, `×`, scrim click, "Close settings") call the same `onClose` prop** — the established single-handler convention from `24-UI-SPEC.md`/`25-UI-SPEC.md`, never a bespoke handler per trigger.

**Three entry points (SET-01):**
1. **⌘,/Ctrl+, global keydown listener** — added to `WorkspaceShell.tsx`, mirroring the existing ⌘K listener's structure (`event.preventDefault()` unconditionally, fires regardless of which element has focus, a second press while already open is a no-op).
2. **Toolbar gear** (`Toolbar.tsx` — currently renders with no `onClick`; this phase wires one). No visual change to the icon itself.
3. **Toolbar theme chip** (`Toolbar.tsx` — currently renders `themeName` with the `.ws-chip` class but no `onClick`; this phase wires one). Its existing `.ws-chip:hover` accent-border treatment becomes meaningful now that the chip is actually clickable; no new CSS is needed.

**Overlay coexistence — the one behavior this phase must resolve that the handoff's simpler `closeAll` model does not address:** the palette and create slide-over's scrims are `position: absolute; inset: 0` at `--z-overlay: 200`, which — because `.ws-toolbar` has no `position`/`z-index` of its own — visually and pointer-wise **covers the entire toolbar**, including the gear and theme chip, whenever either is open. Entry points 2 and 3 above are therefore already unreachable by mouse while the palette or create slide-over is open, with no extra disabled-state styling required (the existing scrim already blocks the click, the same way it blocks every other toolbar control today). The keyboard entry point (⌘,) has no such natural block, so it needs an explicit rule:

- ⌘, while the **palette** is open: closes the palette, opens Settings — the same one-overlay-at-a-time swap `24-UI-SPEC.md`'s ⌘K listener already performs in the other direction.
- ⌘, while the **create slide-over** is open in its `form`, `error`, or `done` step: closes it via its standard `onClose` (a plain close — nothing is written or lost in any of these three steps) and opens Settings.
- ⌘, while the create slide-over is actively **`scanning`** (foreground): **a no-op** — reuses the exact "disabled while a scan is running" precedent `25-UI-SPEC.md` already established for the `+New` pill and the empty-state CTAs, rather than letting the ⌘, shortcut become an undocumented fourth path into CRT-09's cancel-on-close contract. Settings simply does not open; nothing else changes.
- Once open, Settings visually and functionally owns the screen alone (all lower overlays are already closed by the swap logic above) — this is the same "one overlay owns the screen" model `24-UI-SPEC.md`/`25-UI-SPEC.md` already established, extended to a third overlay rather than a new model.
- A **backgrounded** scan (panel already closed via "Run in background") is completely unaffected by any of the above — its status bar segment is visually covered by the Settings scrim while the dialog is open (the scrim covers the full `.ws-root` including the 26px status bar, identical to how the palette/create scrims already cover it today), but the scan itself keeps running in Go regardless of any UI mount state, per `25-UI-SPEC.md`'s Background Handoff Contract. Closing Settings reveals the still-running segment exactly where it left off.

## Theme Section (SET-02)

Section label "Theme" (11px/600 uppercase, `letter-spacing: 0.05em`, `--dm`). Grid: `grid-template-columns: 1fr 1fr; gap: 8px`, 11 cards rendered in `frontend/src/themes.ts`'s `themes` array's literal declared order (storcat-light, storcat-dark, dracula, solarized-dark, solarized-light, nord, one-dark, monokai, github-light, github-dark, gruvbox-dark) — **do not re-sort alphabetically or by type**, matching the array order the demo's own `THEMES.map` iterates.

Each card (`display: flex; align-items: center; gap: 10px; padding: 8px 10px; border-radius: 8px; cursor: pointer`):
- 4-swatch strip (`display: flex; gap: 2px; flex: none`), each swatch `9×18px`, sourced from the theme's own base tokens — **`sw1 = bg, sw2 = p2, sw3 = ac, sw4 = tx`**, read directly from the demo's literal `themeCards` mapping (line 1080); note `sw2` is `p2`, not `p` — the README's plain-English "background, panel, accent, text" description is imprecise about which panel token, the literal code wins. Outer two swatches get corner radius (`2px 0 0 2px` first, `0 2px 2px 0` last), inner two square.
- Name (12.5px/500, `overflow: hidden; text-overflow: ellipsis; white-space: nowrap`) — color `--ac` when this card's theme is the active one, `--tx` otherwise.
- Type tag (`margin-left: auto; flex: none`) — `"light"` or `"dark"`, 11px mono `--fn` (rounded up from the demo's literal 10px, see Typography).
- Card fill/border: `--sel` fill + 1px `--ac` border when active; `--p2` fill + 1px `--l` border otherwise.

**Click applies the theme immediately** (`26-CONTEXT.md`: "Theme applies immediately on click ... No apply-on-close") — calls the existing `applyTokens()` synchronously (same code path `themeTokens.ts` already exposes) and persists the new `themeId` to the Go config (single source of truth, per `26-CONTEXT.md`'s persistence-migration decision) with no intermediate "unsaved" state and no dialog close. The dialog stays open; the user can click through several theme cards in a row and see each repaint instantly, exactly as `THEME-01` already requires elsewhere in the app.

## Layout Section (SET-03) — the segmented control

Section label "Layout" (same 11px/600/0.05em style). Two identically-structured rows, each `display: flex; align-items: center; gap: 14px`:

| Row | Label (12.5px/500) | Note (11.5px `--dm`) | Options |
|---|---|---|---|
| Row density | "Row density" | "How tight the tree and lists pack" | Compact / Comfortable |
| Catalog rail position | "Catalog rail position" | "Details panel takes the other side" | Left / Right |

Label+note column: `display: flex; flex-direction: column; gap: 2px; flex: 1`. Segmented control: `display: flex; gap: 3px; padding: 3px; border-radius: 8px; background: var(--ch); border: 1px solid var(--l); flex: none`. Each segment: `font-size: 12px; font-weight: 500; border-radius: 6px; cursor: pointer` — density segments `padding: 4px 12px`, rail-position segments `padding: 4px 14px` (the 2px difference is literal handoff geometry, see Spacing Scale). Active segment: `background: var(--ac); color: var(--onac)`. Inactive: `background: transparent; color: var(--dm)`.

**ARIA pattern (`26-CONTEXT.md`: "Segmented-control markup and its ARIA pattern" is Claude's Discretion) — resolved as `role="radiogroup"` on the container, `role="radio"` + `aria-checked` on each segment**, not a tablist: a segmented control here is a mutually-exclusive single-choice input (exactly what a native radio group models), not a set of content panels a tab would switch between. Each container carries `aria-label` naming the setting ("Row density" / "Catalog rail position") since the visible label sits in a sibling column, not inside the control itself. Keyboard: the checked segment is the group's one Tab stop (roving `tabIndex`); `ArrowLeft`/`ArrowRight` move the checked state between the two segments and apply immediately (no separate commit step, consistent with SET-05 — there is no "select then confirm" for a 2-option control).

**Clicking (or arrow-navigating to) a segment applies immediately** — same no-save-step model as the theme cards: `density` re-runs `applyTokens()`'s density branch (already wired reactively in `WorkspaceShell.tsx` via its existing `useEffect` on `state.density`), `railSide` flips the grid `order`/divider CSS already established in `22-UI-SPEC.md`'s Layout & Responsive Contract. Both values persist to the Go config with no debounce, per `26-CONTEXT.md`.

## Persistence & Save-as-you-change Contract (SET-05, COMPAT-05)

**Every control in this dialog writes on change, synchronously, with no debounce** (`26-CONTEXT.md`, locked). Visually this means: **there is no Save button, no Cancel button, no dirty-state indicator, and no confirmation-before-close of any kind anywhere in this dialog.** The footer's single button ("Close settings") and the header's `×` are functionally identical — both simply close an already-fully-persisted dialog. This is the direct visual consequence of `SET-05`'s requirement and is why the footer's status line ("StorCat 3.0.0 · settings save as you change them") is load-bearing copy, not decoration — it is the only in-dialog explanation for why there is no Save button.

**No loading state for any control.** Every read (current theme, density, rail side, catalog directory, filename root, four toggles) is already resolved in `AppContext`/local component state by the time the dialog mounts — there is no async fetch on open. Every write is a fire-and-forget config call; the visible control updates optimistically in the same frame the user interacts with it, and does not wait for the Go-side write to resolve before reflecting the new value (consistent with this app's project-wide "no spinners" rule — a spinner on a toggle flip would be exactly the kind of motion-without-meaning that rule exists to prevent).

**COMPAT-05:** the "Remember window size & position" toggle is a visual surface over the pre-existing `windowPersistenceEnabled`/`SetWindowPersistence`/`GetWindowPersistence` config field and bindings (`internal/config/config.go`, unchanged) — flipping it must produce the exact same on-disk effect the pre-milestone preferences toggle already produced. No new visual state is needed beyond the standard toggle rendering above; this row's contract is functional parity, not new UI.
