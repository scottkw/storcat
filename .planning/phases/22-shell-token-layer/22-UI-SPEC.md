# Phase 22 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>

**Derived tokens (computed in TypeScript as concrete `rgb()`/hex values at theme-apply time — CSS `color-mix()` is explicitly banned, WebKitGTK version risk, `PITFALLS.md` #24):**

```
--l2   = mix(l, 55%, p)                          // subtle row separators
--dm   = mix(tx, 66%, bg)                         // secondary text
--fn   = mix(tx, 44%, bg)                         // tertiary/mono metadata
--sel  = mix(ac, 14%, transparent)                // selected row fill
--hov  = mix(tx, 8%, bg)                          // hover fill
--acs  = mix(ac, 16%, transparent)                // accent tint (chips, badges)
--onac = lum(ac) > 0.45 ? '#0b0e13' : '#ffffff'   // text on accent fills
```

Where `mix(a, pct, b)` is an alpha/channel blend performed in TS (equivalent math to the prototype's `color-mix(in oklab, a pct%, b)`, just computed ahead of time rather than shipped as runtime CSS), and `lum` is the relative-luminance helper ported **verbatim** from the prototype (`lum` at line 618 of the demo file):

```js
const lum = (hex) => {
  const h = hex.replace('#', '');
  const v = [0, 2, 4].map(i => parseInt(h.slice(i, i + 2), 16) / 255)
    .map(x => x <= 0.03928 ? x / 12.92 : Math.pow((x + 0.055) / 1.055, 2.4));
  return 0.2126 * v[0] + 0.7152 * v[1] + 0.0722 * v[2];
};
```

`--onac` is what keeps light accents (Gruvbox orange `#fe8019`, Monokai green `#a6e22e`) and dark accents (GitHub blue `#0969da`/`#58a6ff`) both legible on accent-filled buttons/badges (THEME-02). **Verify all 11 themes**, not just the default — this is the single easiest token to get away with hardcoding and the bug only shows on light-accent themes.

All 14 tokens are applied on `:root` via the successor to `App.tsx`'s existing `applyTheme()` — one code path, not a wrapper `<div>`.

## Layout & Responsive Contract (SHELL-01–04, SHELL-09)

```
┌──────────────────────────────────────────────── 46px toolbar ─┐
│ traffic lights · StorCat mark · ⌘K search field · theme · gear │
├─────────────┬───────────────────────────────┬─────────────────┤
│ rail        │ tree 1fr                      │ details         │
├─────────────┴───────────────────────────────┴─────────────────┤
│ 26px status bar                                                │
└───────────────────────────────────────────────────────────────┘
```

- Container: `display: flex; flex-direction: column`, `height: 100vh`. Middle row: `display: grid; grid-template-columns: {cols}; min-height: 0`.
- Every scroll region: `flex: 1; overflow-y: auto; min-height: 0`.
- `scrollbar-gutter: stable` on the rail, tree, and details scroll regions — Windows WebView2 reserves scrollbar width where macOS overlay scrollbars don't; without this the fixed 268px/288px panes truncate content differently per platform (`PITFALLS.md` #26).

| Window width | `grid-template-columns` | Details panel | Rail width |
|---|---|---|---|
| ≥1280px | `268px 1fr 288px` (Left) / `288px 1fr 268px` (Right) | Inline pane, `position: static`, `width: auto`, no shadow | 268px |
| 1040–1279px | `236px 1fr` | Right drawer: `position: absolute; right: 0; top: 46px; bottom: 26px; width: 288px; box-shadow: -24px 0 50px rgba(0,0,0,.45)`, `display: none` unless toggled open via toolbar "Details" chip | 236px |
| <1040px | `200px 1fr` | Same drawer as above tier; tree keeps priority | 200px |

- Rail/details pane `order` is explicit (`1`/`2`/`3`) so the Settings rail-position toggle (Phase 26) can swap sides without re-ordering DOM: rail `order: 1` when Left or narrow (<1280px forces rail to `order: 1` regardless of side setting — the design pins the rail to the visible position even when details becomes a drawer), details `order: 3` when Left / `order: 1` when Right (details drawer position tier is independent of `order` once it's `position: absolute`).
- 1px divider follows the rail's side: `border-right: 1px solid var(--l)` when Left, `border-left: 1px solid var(--l)` when Right (applied to whichever pane is visually adjacent — see the handoff's `railBorderR`/`railBorderL` pair, reused on both rail and details so the divider always sits on the correct edge regardless of order).
- A `useMediaQuery` hook (CSS media queries only, no container queries — same WebKitGTK version risk as `color-mix()`) is the single place React needs to know the tier, used only to decide pane-vs-drawer rendering for the details panel and to show/hide the toolbar "Details" chip. All grid-column swapping is pure CSS.
- Below 1280px the details panel is the **same component**, not a duplicate — rendered into the fixed-position drawer with a backdrop, closable via Escape and backdrop click.

**Below ~820px** the rail becoming a drawer too is explicitly out of scope this milestone (FUT-01, deferred) — do not build it in Phase 22.

## Window Chrome & Drag Regions (SHELL-07, SHELL-08)

- macOS: `TitleBarHiddenInset` (darwin-only Go app option) — real traffic lights render inside the 46px toolbar, ~78px reserved left inset. Windows/Linux: native title bar sits above the 46px toolbar (frameless custom chrome is FUT-02, deferred).
- The 46px toolbar background is the Wails draggable region (`--wails-draggable: drag`), which is **inherited by all descendants** unless explicitly overridden.
- **Every interactive element inside the toolbar band gets an explicit `.no-drag` (`--wails-draggable: no-drag`) class** — established as a project convention here, not just applied ad hoc: search field, theme chip, gear icon, and the responsive-tier "Details" chip (added structurally in this phase even though the drawer toggle behavior is exercised at the 1040–1279px tier). Missing this on any future toolbar addition silently breaks clicks, most visibly on Windows (`PITFALLS.md` #12).
- Traffic-light circles are mock/decorative only in a browser context — Wails supplies the real ones; do not hand-roll click handlers for them.
