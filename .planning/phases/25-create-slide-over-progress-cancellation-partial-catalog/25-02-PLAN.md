<objective>
Give the walk a real error contract and give the write path crash-safety, without changing a single thing the CLI observes.

Purpose: `traverseDirectory` today swallows every read failure completely — an unreadable directory returns as an empty, error-free node and a failed child is dropped with a bare `continue`. Nothing distinguishes "one bad file" from "the SD card was pulled," which is exactly how a scan can appear to succeed while silently missing half a tree. CRT-10 and CRT-11 need that distinction, and the partial catalog they produce needs an on-disk marker plus a write that cannot be truncated by a crash.

Output: an atomic write primitive Phase 27 will reuse, a typed source-loss error carrying the partial tree, and two omitempty marker fields that leave every clean catalog byte-identical.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <decision>The on-disk shape of the unreadable-subtree marker in a partial catalog</decision>
  <context>
This is a one-way door. Once v3.0.0 ships, partial catalogs carrying these keys exist on users' disks and are read by StorCat itself and by whatever external tooling consumes catalog JSON (the compatibility guarantee COMPAT-02 exists to protect). Renaming or restructuring the keys afterwards means every already-written partial catalog silently loses its marker — a migration, not a refactor.

`25-CONTEXT.md` locked the *policy* (mark the affected directory nodes only; never silently omit an unreadable subtree; never split the marker into a sidecar file) and explicitly deferred the *shape* to the research pass. `25-RESEARCH.md` resolved it to two omitempty scalar fields, verified safe because no reader in this repository sets DisallowUnknownFields. The human has not chosen between the shapes, so the door has not been walked through yet.
  </context>
  <options>
    <option id="option-a">
      <name>Two omitempty scalars on CatalogItem: `unreadable` (bool) and `readError` (string)</name>
      <pros>Absent entirely from every clean-scan catalog, so COMPAT-02 holds with no byte drift. Trivially ignorable by every existing reader. Flat — no nested object for external tools to learn. Research's recommendation.</pros>
      <cons>Two keys for one concept; a future third attribute (e.g. an error timestamp) means a third top-level key rather than a growable object.</cons>
    </option>
    <option id="option-b">
      <name>One omitempty nested object: `unreadable: { reason, at }`</name>
      <pros>Growable without adding top-level keys; groups the concept.</pros>
      <cons>A nested object is more work for a shell/jq consumer to test for presence; the truthiness check becomes an existence check. No current need for a second attribute — speculative structure.</cons>
    </option>
    <option id="option-c">
      <name>A single omitempty string `readError`, with presence implying unreadability</name>
      <pros>One key; simplest possible shape.</pros>
      <cons>Conflates "was unreadable" with "has a reason string" — an unreadable node with an empty reason becomes indistinguishable from a clean node, which is exactly the invisible-data-loss failure this marker exists to prevent.</cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c</resume-signal>

## Flagged assumptions (unresolved probe rows owned by this plan)

The classification heuristic implemented here (re-probe the scan root on any read failure) is derived from `25-RESEARCH.md`'s Pitfall 2 and from a physical-media failure model, not from a machine-checked category sweep.
