## Color

**This is the phase's one genuinely new color decision.** The handoff (`README.md` §5) already assigns three of the four colors this phase needs — `added: --ac`, `removed: #e5534b`, `changed: #f0b429`, `unchanged: --dm` — but its stat array and its literal `diff` mock data (`StorCat 1a Demo.dc.html` line ~1029) predate `28-CONTEXT.md`'s decision that **unreadable is a genuine fifth category, not a shade of removed.** The handoff has no token left to give it: accent, danger, and warning are all already claimed by added/removed/changed respectively, and `--dm` is claimed by unchanged (which isn't even colored — it's neutral/count-only).

**Resolution: `unreadable` reuses `--danger` (`#e5534b`) — the same token as `removed` — differentiated by glyph and grouping, not by hue.** A sixth theme-independent literal color was considered and rejected:

- This app has kept its status-color set deliberately small and fixed across all 11 themes for three phases running (`22-UI-SPEC.md`'s error/warning pair, formalized into `--danger`/`--ondanger` in `27-UI-SPEC.md`). A new hue would need re-verifying for legibility against all 11 themes' *own* accent colors, not just against `--bg`/`--p` — and at least one existing accent already sits close on the wheel to a plausible "new" status hue (Dracula's `--ac: #bd93f9` is a light purple; Gruvbox Dark's `--ac: #fe8019` and the existing warning `#f0b429` are both already warm-orange-adjacent). Every additional fixed hue this app adds is another 11-theme collision surface to maintain forever; reusing an existing, already-verified token avoids that entirely.
- `removed` and `unreadable` are never ambiguous in practice because they are never rendered in the same visual context: they sit in **separate, individually-headed groups** in the diff list (see Diff List Contract) — a row can only be read as "REMOVED" or "UNREADABLE" by way of the section header it sits under, the same way this app already disambiguates same-colored elements elsewhere (e.g. `--ac` alone marks both "selected row" and "success," disambiguated by context, not by a second hue).
- The glyph itself carries real semantic weight here: `!` is not arbitrary — it is the **exact glyph** `UnreadableCatalogPanel`'s badge and `ErrorBody`'s round badge already use for "this could not be read," so a user who has seen either of those surfaces already recognizes it. Reusing `--danger` for the same glyph is consistent, not a corner-cut: the two things genuinely share the same underlying cause (a read failure), even though CONTEXT is right that they must never be *collapsed* into one diff category.

| Role | Value | Usage |
|------|-------|-------|
| `--ac` | theme-dependent | Added-state rows/tile/mark; `RescanDialog`'s "Overwrite catalog" primary button (handoff-literal — see the note under Resolution Footer for why this is *not* `--danger`-styled despite being destructive) |
| `--danger` (`#e5534b`) | fixed | Removed-state rows/tile/mark; Unreadable-state rows/tile/mark (same token, see resolution above); reused verbatim from `27-UI-SPEC.md`, no new declaration |
| Warning (`#f0b429`) | fixed | Changed-state rows/tile/mark (handoff-literal — this app's existing "read errors"/"partial" warning color, already theme-independent per `22-UI-SPEC.md`'s status table); the similarity-warning banner (new usage of the same token — see Similarity Warning Contract) |
| `--dm` | theme-dependent | Unchanged-state tile (count only, no rows — handoff-literal); Discard footer button text |

**Accent reserved for (additive to Phases 22–27's lists — nothing removed):**
- Added-state diff rows/tile/mark
- `RescanDialog`'s "Overwrite catalog" primary button fill

**Destructive (`--danger`) reserved for (additive):**
- Removed-state diff rows/tile/mark
- Unreadable-state diff rows/tile/mark
- `UnreadableCatalogPanel`'s "Remove from library" button text (unchanged, already declared in `23-UI-SPEC.md`'s precedent for the `!` badge)

**Warning (`#f0b429`) reserved for (additive — this phase is only its third consumer, after the volume-card "read errors" tag and the done-state "partial" tag, both `25-UI-SPEC.md`):**
- Changed-state diff rows/tile/mark
- Similarity-warning banner (text + `rgba(240,180,41,.14)` background, same tint literal already used for the other two consumers)

## Architecture & State — read before implementing

**`state.rescan` is a new, separate `AppContext` reducer slice — it does not extend or replace `state.scan`.** This is the load-bearing decision the rest of this document depends on, so it is stated up front rather than only implied by the component sections below.

- **Live scan progress is shared.** `RescanDialog`'s scanning step dispatches the exact same `SCAN_STARTED` / `SCAN_PROGRESS` / `SCAN_FAILED` actions Create already uses, driving the exact same `state.scan` slice, subscribed to the same always-on `scan:progress` `EventsOn` listener (`CreateSlideOver.tsx`'s existing subscription — do not add a second one). This is correct, not a shortcut: `28-CONTEXT.md` confirms re-scan reuses the same `scanMu`/`activeScanCancel` one-scan-at-a-time guard on the Go side, so the two flows are already mutually exclusive at the backend; sharing the frontend's progress slice makes that guarantee visible for free — the existing `isScanningNow` check (`state.scan.status === 'counting' || 'scanning'`) that already disables "+ New" and the tree-empty-state CTAs during a Create scan now *also* correctly disables during a re-scan, with no new code.
- **The terminal outcome is not shared.** On success, `RescanDialog` does **not** dispatch `SCAN_DONE` (that shape is `ScanResultFile[]` — written files — which a re-scan does not have until a resolution is chosen). It dispatches a new action (name at planner's discretion, e.g. `RESCAN_DIFFED`) that populates `state.rescan.diff` and, in the same reducer transition, resets `state.scan` back to `{ status: 'idle' }` so the shared progress slice never lingers in a stale terminal state for the *other* flow.
- **No background hand-off for re-scan, by deliberate scope decision — not an oversight.** Closing `RescanDialog` during its scanning step (Escape / `×` / scrim) **cancels the scan** (calls `wailsAPI.cancelScan()`, same as Create's `handleCloseRequest('cancel-the-scan')`), it never backgrounds it. This is why sharing `state.scan` causes no dead-end: the status-bar's `● scanning {name} · {pct}%` segment's click handler (`25-UI-SPEC.md`'s Background Handoff Contract, hardcoded to reopen `CreateSlideOver`) can never actually fire mid-re-scan, because `RescanDialog`'s own scrim covers the entire app (including the status bar) for the whole time `state.scan.status` could read `'scanning'`/`'counting'` from a re-scan — and the moment `RescanDialog` closes, that state is cancelled back to `'idle'` before the status bar is ever visible again. No `kind: 'create' | 'rescan'` discriminant is needed anywhere; do not add one speculatively.
- **`ScanningBody` and `ErrorBody` (`frontend/src/components/workspace/create/`) are reused verbatim, with two additive, optional props — not forked.** `ScanningBody`'s `onRunInBackground` becomes optional; when omitted, the "Run in background" button and its helper text simply don't render (re-scan has none to background). `ErrorBody`'s `writingPartial`/`onWritePartial` become optional together; when both are omitted, the "Write partial catalog" button doesn't render and **"Retry scan" is promoted to the primary-styled slot** in its place (exactly one strong CTA should exist in that footer either way). This is the correct extension shape — additive optional props on an already-tested component, the same pattern `27-CONTEXT.md` used for `DetailsPanelProps` — not a second copy of either component.
- **Why re-scan gets no partial-write option in its error state:** a partial *diff* (comparing a fully-loaded old tree against a half-walked new one) has no well-defined resolution — `28-CONTEXT.md`'s Deferred Ideas explicitly rule out per-entry/partial reconciliation. If the volume disappears mid-re-scan, the only offered paths are "Retry scan" and "Close without writing" — the existing catalog is completely untouched either way (see Error Step Contract for the exact copy).

This carries no regression risk: `Menu.tsx`'s roving-`tabIndex` keyboard nav is generic over its `items` array (order-agnostic), so re-ordering is a pure data change, not a behavior change.

## RescanDialog — Shell (all steps)

`.ws-rescan-scrim` (`rgba(4,6,9,.62)`, `100ms` fade-only, same keyframe *shape* as `ws-dialog-scrim-in`/`ws-settings-scrim-in` but its own declaration per this app's now-three-times-repeated "own declaration per genuinely distinct consumer, even at identical values" convention) → `.ws-rescan-panel` (620px, radius 12px, `--p` fill, 1px `--l` border, shadow `0 30px 70px rgba(0,0,0,.6)`).

**Header (50px, 1px bottom border `--l`):** title (15px/600, varies per step — see each step's own section) + step label (11px mono `--fn`, `"step 1 of 3"` / `"step 2 of 3"` / `"step 3 of 3"` / `"failed"`) + `×` (16px `--dm`, `aria-label="Close"`, `margin-left: auto`).

**All four close paths — Escape, `×`, scrim click, and the footer's "Discard scan and close" (diff step only) — write nothing and require no confirmation, at every step.** This mirrors `25-UI-SPEC.md`'s Cancellation Contract exactly: nothing is written to disk until a resolution button is explicitly clicked, so there is nothing a confirmation would protect. During the scanning step specifically, closing also cancels the underlying scan (see Architecture & State above).

**Mount pattern:** conditionally mounted by its parent (rendered only while open) — no exit animation to preserve beyond the shared `100ms` scrim fade, same reasoning `Menu.tsx` and `DialogShell` already use.

## Error Step — Scan Interrupted

Triggered identically to CRT-10 (the picked volume vanishes mid-walk). Header title: **"Scan interrupted"**. Step label: `"failed"`.

Body: renders the existing `ErrorBody` component unmodified — round `!` badge, headline `"Stopped at {pct}% — the volume went away"`, mono sub-line, error log, actions row — with `writingPartial`/`onWritePartial` **omitted** (so "Write partial catalog" doesn't render and "Retry scan" takes the primary slot), and **one corrected line**: the explanatory paragraph. `ErrorBody`'s existing copy ("Nothing was written yet...") is Create-specific — it reassures about a catalog that doesn't exist yet. ## Step 3 — Diff & Resolve

Two content variants sharing one header/footer shell, selected by whether an old, parseable tree exists to compare against (`oldTreeAvailable`, set at the entry point — `true` from the catalog-actions menu / details-panel footer, `false` from `UnreadableCatalogPanel`).

### Variant A — Full diff (`oldTreeAvailable: true`)

Header title: **`"Re-scan changed {N} entries"`** where **`N = added + removed + changed + unreadable`** (never includes unchanged — handoff-literal phrasing and arithmetic, verified against the handoff's own mock data: `312 added + 18 removed + 4 changed = 334`, exactly its literal title). Step label: `"step 3 of 3"`.

**Invariant the planner and executor must hold:** the five stat-tile values (added, removed, changed, unreadable, unchanged) must sum to the total number of distinct paths encountered across the old tree ∪ the new tree combined. This is the same "count sums against its own table" discipline `27-UI-SPEC.md` held and `26-UI-SPEC.md` did not — stated here explicitly since this phase is the one that introduces a 5-way count for the first time.

Body (padding 16px 18px 14px, flex column, gap 14px):

1. Mono sub-line (11.5px, `--dm`): `"{catalogFilename} · scanned {sourcePath} just now"` (handoff-literal).
2. **Similarity warning** (conditional — see its own contract below), rendered here, above the stat grid, when present.
3. **Stat-tile grid** — `grid-template-columns: repeat(5, 1fr); gap: 8px`. One tile per state, each `padding: 9px 11px; border-radius: 8px; background: var(--ch)`, column layout `gap: 3px`:

   | Tile | Value format | Color | Label |
   |---|---|---|---|
   | Added | `"{n} files"` | `--ac` | "added" |
   | Removed | `"{n} files"` | `--danger` | "removed" |
   | Changed | `"{n} files"` | `#f0b429` | "changed" *(corrected from the handoff's literal "changed size" — `28-CONTEXT.md` adds mtime to the comparison, so "size" alone is no longer accurate; the value itself is unchanged, only the label word)* |
   | Unreadable | `"{n} files"` | `--danger` | "unreadable" *(new tile — `28-CONTEXT.md`'s fourth diff state)* |
   | Unchanged | `"{n} files"` | `--dm` | "unchanged" |

4. **Diff row list** — see Diff List Contract below.
5. **Resolution caption** (11.5px, `--dm`, line-height 1.5, always visible — not conditional): see Resolution Footer Contract.

### Variant B — Reduced, no diff (`oldTreeAvailable: false`, STATE-03's path)

Header title: **"Scan complete"** *(deliberately does not say "Catalog rebuilt" — the scan alone fixes nothing; the original unreadable catalog stays exactly as broken until a resolution is chosen, and "Keep both" specifically leaves it untouched, so the title must not presuppose which resolution the user will pick)*. Step label: `"step 3 of 3"`.

Body: no stat grid, no diff row list, no similarity warning (there is no old tree to compare cardinality against — not applicable, not "resolved elsewhere"). ## Diff List Contract

**Not built on `@tanstack/react-virtual` or `TreePane`'s `useVisibleRows` hook — a plain scrollable `<div>`, `max-height: 200px; overflow-y: auto`.** Two independent reasons, stated so this isn't mistaken for an oversight of the phase brief's explicit prompt to consider reuse:

1. **Structurally, a diff has no hierarchy to reuse.** `TreePane`'s virtualizer pairs with `useVisibleRows`, which exists specifically to resolve parent-expanded/child-visible state for a nested tree. A diff row's `Name` field is already the full relative display path (`28-CONTEXT.md`: "It already holds the full relative display path... set once from `filepath.Rel`"), so every row renders flat, with no expand/collapse interaction and no parent/child relationship to track. Reusing `useVisibleRows` here would mean building fake single-level "always expanded" tree state for data that was never a tree — more code, not less.
2. **Scale is bounded by what actually differs, not by catalog size.** The tree pane's 40k-node virtualization exists because a *whole catalog* can be that large and is always fully rendered. A diff list only ever contains entries that changed — for any realistic re-scan (a card that gained/lost/edited some files since last cataloguing), that is a small fraction of the total. At `200px` visible height (≈7–8 rows at the row heights below), a native-scroll `<div>` handles even a few thousand DOM rows without a dropped frame; there is no smooth-scroll requirement here the way there is for the always-visible tree pane.

**🧪 Backstop, stated explicitly rather than silently assumed:** if a pathological re-scan produces tens of thousands of differing rows (e.g. re-scanning against a catalog of the wrong disc entirely — exactly the case the similarity warning exists to flag *before* this point), native-scroll performance is not verified against that scale. This is a reasoned boundary call, not a proven one; if it ever needs revisiting, `@tanstack/react-virtual` is already a dependency and the tree pane's own `useVirtualizer` usage (flat mode, no `useVisibleRows`) is the direct template.

**Grouping and order:** four groups, in this fixed order — **Added, Removed, Changed, Unreadable** (unchanged entries are never rendered as rows, count-only in their tile). This order matches both `28-CONTEXT.md`'s own prose order and `ACT-06`'s literal requirement wording, so it needed no invention. Within each group, rows sort alphabetically by path (no new sort logic — matches conventional file-manager ordering). **A group with zero entries is omitted entirely** — no "REMOVED (0)" header — same "no reserved empty slot" rule the status bar's conditional segments, the delete dialog's conditional `.html` row, and the volume picker's card list all already follow.

**Group header row** (24px, `11px/600 uppercase 0.05em --dm`, no background): `"{STATE} · {n}"`, e.g. `"REMOVED · 18"`.

**Entry row** (`padding: 7px 0; border-bottom: 1px solid var(--l2)`, gap 10px):
- Mark column (`width: 10px; flex: none`, 12px mono): `+` (added, `--ac`) / `−` (removed, `--danger`) / `~` (changed, `#f0b429`) / `!` (unreadable, `--danger`).
- Path (11.5px mono, `flex: 1; overflow: hidden; text-overflow: ellipsis; white-space: nowrap`) — single-line ellipsis, **not** the delete dialog's `word-break: break-all`/never-truncate treatment: this is a scan list of potentially hundreds of rows, not a single path the user must verify character-for-character before an irreversible action.
- Right column (`margin-left: auto; flex: none; white-space: nowrap`, 11px mono `--dm`):
  - Added/Removed rows: the entry's size (`formatBytes`).
  - Changed rows: `"{oldSize} → {newSize}"` (per `README.md` §5's literal "old → new" option).
  - Unreadable rows: the short read-error reason (e.g. `"permission denied"`) in place of a size — reusing the exact vocabulary `ErrorBody`'s log lines already use, not inventing new error taxonomy; no size is shown because none is knowable for an entry that failed to read.

## Similarity Warning Contract

Rendered above the stat-tile grid, in Variant A only (there is no baseline to compare against in Variant B). `padding: 10px 12px; border-radius: 8px; background: rgba(240,180,41,.14); color: #f0b429; font-size: 11.5px; line-height: 1.5` — reuses the exact tint literal already declared for the volume-card "read errors" tag and the done-state "partial" tag (`25-UI-SPEC.md`), this phase's third consumer.

Copy (dynamic): **"This looks like a different volume than the one this catalog came from — {added + removed} of {total} entries differ. Double-check before overwriting; a large, legitimate change is still possible."**

**Never blocks.** No button in the footer is disabled by this banner's presence — `28-CONTEXT.md`: "the app cannot know the user is wrong, and a legitimately enormous change must stay possible." The banner is purely informational, sitting above the same three always-enabled resolution actions.

**Trigger condition (Claude's Discretion per `28-CONTEXT.md` — a concrete default, not a hard requirement):** `(added + removed) / total ≥ 0.6`, where `total` is the same denominator the invariant above uses (all five categories summed), and only evaluated when the old catalog had at least, say, 20 entries (avoids a false-positive "near-total change" reading on a catalog that was always tiny). The exact threshold and floor are the planner's to tune; this default exists so the UI has a concrete, testable condition to build against rather than an unspecified one.

## Resolution Footer Contract (ACT-07)

**56px, `--p2` background, 1px top border `--l`, buttons left-clustered, `Discard` isolated far right via `margin-left: auto`** — this phase follows the Create-flow footer convention (primary-cluster-left, tertiary-isolated-right, as `CRT-04`'s form footer and `ErrorBody`'s own footer both already do), not the Rename/Delete dialog convention (secondary-then-primary, right-aligned as one group) — `RescanDialog` is a multi-step flow in the same family as Create, not a single-screen confirmation, and this keeps it visually consistent with its closest sibling.

**Order and exact copy — locked, none of the three may be shortened to a bare word:**

1. **"Overwrite catalog"** — primary, 32px, `padding: 0 15px`, radius 8px, **`--ac` fill / `--onac` text**, 12.5px/600 (handoff-literal color — despite being the destructive option, the handoff does not danger-style it, and `28-CONTEXT.md` does not override that color choice; the destructiveness is instead made unmistakable through the caption paragraph below, not through button color). Calls `WriteCatalogFrom` against the original catalog's own path (and its `.html`, only if one already existed — `28-CONTEXT.md`'s "never created where none existed" rule, unchanged from how it governs Overwrite generally).
2. **"Keep both (write {root}-copy.json)"** — outlined, 32px, `padding: 0 14px`, radius 8px, 1px `--l` border, 12.5px, default text color. `{root}` is the *original* catalog's filename root (`catalog.filename` with `.json` stripped) — e.g. `sd12.json` → `"Keep both (write sd12-copy.json)"`. This is a **first-candidate preview label**, not a collision-checked guarantee: if `sd12-copy.json` already exists by the time the write actually happens, the backend's existing `-copy`/`-copy-2`/… loop (`internal/catalog/duplicate.go`, reused per `28-CONTEXT.md`) silently resolves to the next free name, exactly as Duplicate already does today with zero frontend pre-validation. Do not build a live collision-check call just to keep this label perfectly accurate — that would be new binding surface for a cosmetic guarantee this app has never made anywhere else.
3. **"Discard scan and close"** — text, no border, `--dm`, 12.5px, `margin-left: auto`. *(Not bare "Discard" — the handoff's literal label — per this phase's explicit copy constraint: it must name what's discarded. This is a direct, minimal extension of this app's own already-established "Discard and close" phrase from `CRT-01`'s Create form footer, just naming the object: the scan, not the whole flow.)*

**Resolution caption (always visible, directly above the footer, 11.5px `--dm` line-height 1.5) — the "name what's written and lost" requirement:**

- Variant A (full diff): *"Overwriting replaces {catalogFilename}'s current contents with this scan's results — the previous version can't be recovered. Choose Keep both instead if you want to preserve it."*
- Variant B (reduced, STATE-03 path): *"Overwriting rebuilds {catalogFilename} in place from this scan. Choosing Keep both leaves {catalogFilename} exactly as unreadable as it is now, and saves this scan separately."*

**Why this is stronger, not weaker, than Phase 27's Delete confirmation despite using a non-red button:** Delete moves files to the OS Trash — recoverable until emptied, and its copy says so plainly ("you can restore them from the Trash until it's emptied"). Overwrite here has **no such recovery path** — the old catalog's bytes are gone the instant `WriteFileAtomic`'s `os.Rename` completes, with no Trash step at all (`28-CONTEXT.md`: reuses `WriteCatalogFrom` wholesale, the same atomic rewrite, not a trash-then-write). The caption above says exactly this ("can't be recovered"), which is the one respect in which this dialog's language is *more* absolute than Delete's, even though its button isn't `--danger`-colored. Do not soften this copy to imply any undo path exists — none does.
