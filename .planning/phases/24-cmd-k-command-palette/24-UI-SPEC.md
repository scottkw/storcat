## Color

No new base tokens. One new **literal** scrim value and one new class-scoping decision; everything else reuses Phase 22/23 tokens.

| Role | Value | Usage |
|------|-------|-------|
| Scrim | `rgba(4,6,9,.62)` | Palette overlay background — **distinct from** the narrow-tier details-drawer backdrop's `rgba(0,0,0,.35)` (`.ws-backdrop` in `workspace.css`). This is not an inconsistency to fix: the handoff itself uses two different scrim values for a drawer-beside-content overlay versus a true modal dialog, and `22-UI-SPEC.md`'s shadow table already treats palette/modal shadows as their own class distinct from the drawer's shadow for the same reason. Declare as a new literal (not a token) since only this surface and the future create-slide-over/Settings modal (Phase 25/26, which reuse the same overlay pattern per the handoff) use it. |
| Accent (`--ac`) | theme-dependent | Magnifier icon in the palette header (15px, `--ac`, not `--dm` — differs from the toolbar magnifier); match-highlight substring inside a result-row basename (`color: var(--ac); font-weight: 600`); catalog chip text |
| `--acs` | theme-dependent tint | Catalog chip fill |
| `--hov` | `mix(tx,8%,bg)` | Result-row hover **and** the keyboard-active row (see Interaction Contract — the two states share one visual, they are not distinguishable by color) |
| `--fn` | `mix(tx,44%,bg)` | Header hint text, footer hint text, result-row size text is `--dm` not `--fn` (see table above — do not swap these) |

**Accent reserved for (additive to Phase 22/23's list — nothing removed):**
- Palette header magnifier icon (15px, `--ac` stroke — the one icon in the app that is accent-colored by default, not just on hover)
- Match-highlight substring within a result row's basename only (never the path)
- Catalog chip text (on `--acs` fill)

**Catalog chip — resolves a literal-vs-intent tension in `24-CONTEXT.md`:** the context decision says to reuse "the existing `.ws-chip` token/class for the catalog chip rather than new styling." Read literally, `.ws-chip` (`workspace.css`) is a **hover-only** rule (`color`/`border-color` shift to `--ac` on `:hover`) applied to the *outlined, interactive* toolbar theme chip — its base look (transparent fill, `--dm` text, 1px `--l` border) is set inline at each call site, and its `:hover` behavior assumes the chip is clickable. The handoff's actual palette catalog chip (line 259 of the demo file) is a **static, non-interactive, filled** badge: `color: var(--ac); background: var(--acs); border-radius: 5px; padding: 2px 7px; font-size: 11px` — it has no `onClick` and the handoff defines no hover state for it. Applying `.ws-chip`'s hover rule to a label with no click target would be misleading (it would visually promise interactivity that doesn't exist). Resolution: follow the **intent** — reuse the project's established chip-naming/class convention (as `.ws-dir-chip` already does for a differently-styled, differently-behaved chip sitting alongside `.ws-chip`) — by adding a new sibling declaration `.ws-palette-chip` in `workspace.css` for the filled/static look, rather than repurposing `.ws-chip`'s hover CSS for a non-interactive element. This is not "new styling" in the sense the context decision was guarding against (no new token, no new color, no new radius/padding value — every value is already in the locked scale); it is the same chip-family pattern the codebase already uses twice.

**No new destructive-color usage.** `#e5534b` is not used anywhere in this phase's scope.

## Palette Contract (PLT-01–07)

### Overlay & panel shell

- Scrim: `position: absolute; inset: 0; background: rgba(4,6,9,.62); display: flex; justify-content: center; padding-top: 15vh; z-index: var(--z-overlay)`. Click on the scrim (not the panel) closes the palette — the panel gets its own click handler that stops propagation, matching the handoff's `onClick={{stop}}` convention (already the pattern the future create slide-over and Settings modal will need from the shared hook's consumer contract, even though this phase only builds one instance of it).
- Panel: `width: min(640px, calc(100vw - 32px)); max-height: min(520px, 70vh); border-radius: 12px; background: var(--p); border: 1px solid var(--l); box-shadow: 0 30px 70px rgba(0,0,0,.6); display: flex; flex-direction: column; overflow: hidden`.
- Transition: **100ms scrim fade, no movement** — exactly the handoff's documented rule for "Modals and the ⌘K palette." No slide/scale animation on the panel itself.
- No close (`×`) button on the panel — the handoff's palette markup has none (unlike the future create slide-over's header, which does). Close paths this phase: Escape, scrim click, selecting a hit (auto-closes after dispatching the reveal).

### Input row (50px, 1px bottom border `--l`)

- Magnifier: 15×15px SVG, `stroke="var(--ac)"`, `stroke-width: 1.6` — reused shape from Phase 22's toolbar icon, different size/color as noted above.
- Input: `flex: 1`, mono, 14px, `color: var(--tx)`, no visible border/background of its own (the panel border is the only chrome) — matches the handoff's bare `<input>`.
- Placeholder: **not the handoff's static demo string.** Compute live from already-available data: `Search {formatCount(totalIndexedFiles)} files across {catalogCount} catalogs…`, where `totalIndexedFiles` is the same rail-derived sum the status bar already computes (`23-UI-SPEC.md`'s Status Bar Contract) and `formatCount` is the existing `frontend/src/lib/format.ts` helper. "catalogs" stays unconditionally plural regardless of count — this extends, not invents, the project's established "always plural, no singular special-case" convention (`23-UI-SPEC.md`'s rail-row line-2 rule). A zero-catalog directory renders "Search 0 files across 0 catalogs…", consistent with the status bar's own accepted zero-state literal.
- Right-aligned hint/count text: 11px mono `--fn`, four mutually exclusive values (see States below): `"Type to search…"`, `"Searching…"`, `"{total} hits"` (always plural, same convention), `"50 of {total}"`.
- Autofocus: the input receives focus synchronously when the palette opens (PLT-01) — this is the shared hook's job (initial-focus target), not a bespoke `useEffect` in the palette component.

### Result row (`padding: var(--hp)`, no border-radius, `gap: 8px`, cursor pointer)

- Shape: 8×8px, `border-radius: 2px` + `--ac` fill for a directory hit, `border-radius: 50%` + `--fn` fill for a file hit — same shape/color convention as `23-UI-SPEC.md`'s tree-row shapes, reused verbatim rather than invented fresh for this surface.
- Name + path column (`flex: 1; min-width: 0; display: flex; flex-direction: column; gap: 2px`):
  - Basename: 12.5px mono, ellipsized. The matched substring (case-insensitive `indexOf` of the query against the basename; **first occurrence only** if the query appears more than once — no multi-span highlighting) renders as `<span style="color: var(--ac); font-weight: 600">`; the rest of the basename stays `var(--tx)` at weight 400. If the query matched only in the path (not the basename), the basename renders entirely unstyled — never fabricate a highlight where none exists.
  - Path: 11px mono, `var(--dm)`, ellipsized, **never highlighted** (locked in `24-CONTEXT.md`: "The path stays plain-dimmed").
- Catalog chip: `.ws-palette-chip` (see Color section) — 11px, `color: var(--ac)`, `background: var(--acs)`, `border-radius: 5px`, `padding: 2px 7px`, `flex: none`.
- Size: 11px mono, `var(--dm)`, `flex: none; white-space: nowrap; width: 74px; text-align: right` — reuses `frontend/src/lib/format.ts`'s `formatBytes`, not a new formatter.
- Row background: `--hov` on mouse hover **and** on the keyboard-active row (single shared visual — see Interaction Contract). Transparent otherwise. No selected-row persistence after the palette closes (unlike rail/tree rows, a palette result has no "currently selected" concept once you've navigated away from it).
- Flat list, backend order (catalog, then path) — **no grouping, no sticky catalog headers**, locked in `24-CONTEXT.md`.

### States (mutually exclusive, exactly one renders in the scroll region below the input row)

1. **Hint** — `query.trim().length < 2`: centered text, 12.5px, `var(--dm)`, `padding: 30px 14px` — copy: `"Type to search…"`. This is a **distinct state from the empty-result state**; PLT-06's exact string never renders for a query that was never actually run (locked in `24-CONTEXT.md`).
2. **Searching (quiet)** — query is ≥2 chars, a debounced request is in flight, and there is no previously-settled result set for *any* query to keep showing (i.e., only the very first keystroke-triggered search in a session shows this; subsequent keystrokes keep the prior results visible until the new response lands, avoiding a flash on every character). Same visual treatment as state 1 but copy `"Searching…"` — **no spinner**, per the handoff's "No spinners — progress is always a real number" rule, already carried into every prior phase's UI-SPEC.
3. **Results** — flat list of up to 50 rows, `padding: 6px 0` on the scroll container. If `total > 50`, append a truncation line below the last row: `padding: 10px 14px; border-top: 1px solid var(--l2); font-size: 11.5px; color: var(--dm); line-height: 1.5` — copy **exactly** `"Showing the first 50 of N hits"` (PLT-03, locked in `24-CONTEXT.md` — the handoff's longer "…refine the term, or ↵ to open the full result table." suffix is dropped; there is no full-table view in this phase's scope).
4. **No matches** — the debounced query settled with `total === 0`: centered text, `padding: 30px 14px; text-align: center; font-size: 12.5px; color: var(--dm)` — copy **exactly** `"No file in any catalog matches that."` (PLT-06, verbatim).

### Footer (32px, `--p2` background, 1px top border `--l`, mono 10.5px `--fn`)

Three segments, left/left/right (matches the handoff exactly): `"↵ reveal in catalog"`, `"esc close"`, right-aligned `"searches names and paths"`.

## Interaction Contract (PLT-04, PLT-05, PLT-07)

- **Open triggers (PLT-01):** clicking the toolbar's `.ws-search` button (`frontend/src/components/workspace/Toolbar.tsx` — currently has no `onClick`; this phase adds one) **and** a global `⌘K`/`Ctrl+K` keydown listener. The global listener must not fire while an existing text input has focus in a way that would swallow the shortcut unexpectedly — specifically, it must still fire even while the rail filter input is focused (⌘K is a global override), but must not double-trigger if the palette is already open (a second ⌘K while open is a no-op, not a re-open/re-focus cycle that would discard in-progress typing).
- **Keyboard navigation (PLT-04):**
  - `↓` / `↑` move a single "active" index through the current result list, clamped at the boundaries (no wrap-around — reaching the last result and pressing `↓` again stays on the last result). This is Claude's-discretion territory per `24-CONTEXT.md`; no-wrap is the simpler, more predictable default and avoids a surprising jump when scanning a short list.
  - `Home` / `End` jump the active index to the first/last result.
  - `PageUp` / `PageDown` move the active index by the number of rows currently visible in the scroll viewport (computed, not a hardcoded count) — falls back to a fixed step of 10 if the viewport height can't be read yet (e.g. first render).
  - `Enter` activates the active row exactly as a click would (see Reveal below).
  - `Escape` closes the palette — handled by the shared hook, not a bespoke listener in the palette component.
  - The active row is visually indistinguishable from a hovered row (`--hov` background, see Color section) — moving the mouse over a different row while navigating by keyboard re-targets the active index to whatever the mouse is over (standard combobox behavior: mouse and keyboard share one "active" concept, not two).
  - ARIA: results container `role="listbox"`, each row `role="option"` + `aria-selected` reflecting the active index — parallels the rail's `aria-current`/`data-selected` convention (`23-UI-SPEC.md`) translated to listbox semantics, since a palette result list is a listbox, not a set of buttons.
- **Click a hit / Enter on the active hit (PLT-05):** dispatches the catalog switch (if the hit isn't already the current catalog) plus a reveal request, then closes the palette. The reveal itself — switch catalog → expand every ancestor → select the node → `virtualizer.scrollToIndex(visibleIdx, { align: 'center' })` → clear the request — is `TreePane`'s job per `24-CONTEXT.md`'s `pendingReveal` design (state architecture, not a visual contract; noted here only because "scroll into view, centered" is a visible outcome this UI-SPEC must not contradict). **Directory hits select but do not auto-expand the target directory itself** — only its ancestors — per `24-CONTEXT.md`.
- **Query reset on open:** the input starts empty every time the palette opens — no persisted "last query" across open/close cycles. This is the simpler, more conservative choice given `24-CONTEXT.md`'s Deferred Ideas explicitly rule out "search history / recent queries persistence"; carrying the query forward implicitly edges toward that deferred behavior, so it resets.
- **Debounce:** ~200ms after the last keystroke (locked in `24-CONTEXT.md`), with a stale-response guard so a query whose response arrives after a newer query was issued is dropped, never rendered. This governs when state 2/3/4 above transition, not their visual appearance.
- **Scroll lock & focus trap (PLT-07):** while the palette is open, page scroll behind it is locked and Tab/Shift+Tab cycle only within the palette (input → result rows are not natively tabbable — the listbox pattern uses roving `tabIndex`/arrow-key navigation instead, so realistically the only two tab-stops are the input and... nothing else, since there's no close button; the trap mainly exists to stop focus from leaving into the rail/toolbar behind the scrim). On close, focus returns to whichever element opened the palette (the toolbar search button or wherever focus was when ⌘K fired).

## Shared Modal Behavior Hook Contract

`useModalBehavior({ isOpen, onClose })` in `frontend/src/hooks/useModalBehavior.ts` (locked file location convention, matching `useVisibleRows.ts`/`useMediaQuery.ts`). This phase is the **first and only consumer**, but the hook's API must already generalize to Phase 25's create slide-over (five distinct close paths, an animated exit that must not unmount early) and Phase 26/27's dialogs — per `24-CONTEXT.md`: "Phases 25, 26, and 27 import this hook; they must not reimplement any of these four behaviors." The four behaviors, stated as visible contract (not implementation):

1. **Focus trap** — focus never lands on an element behind the scrim while open.
2. **Escape-to-close** — a global `Escape` keydown while open calls `onClose`, regardless of which element inside the overlay currently has focus.
3. **Scroll lock** — the page behind the scrim does not scroll while open (this phase: locks the whole `.ws-root`; later phases reuse this unchanged).
4. **Focus restore** — on close, focus returns to the element that had focus immediately before the overlay opened (not hardcoded to a specific trigger element, since Phase 25/26/27 will each have a different trigger).

The hook's exact signature/return shape (ref callback vs. object of refs, whether it manages `isOpen` internally or is purely reactive to a caller-controlled `isOpen`) is Claude's Discretion per `24-CONTEXT.md` — this UI-SPEC constrains only the four *visible* behaviors above, since a signature choice has no visual footprint.

### E1 — Palette overlay & panel shell (modal / interactive-control)

### E2 — Palette input & live search (form / interactive-control)

| Category | Status | Resolution |
|----------|--------|------------|
| empty | ✅ explicit | Empty input → hint state (< 2 chars branch covers empty identically to 1-char). |
| loading | ✅ explicit | Debounced 200ms; quiet "Searching…" only on the very first in-flight query of a session (no flash on subsequent keystrokes — prior results stay visible until the new response lands, per the stale-response-guard design). |
| error | ✅ explicit | Same resolution as E1 — no distinct input-level error state. |
| overflow | ✅ explicit | Input `flex: 1`, no visible max-length; a pathologically long query simply scrolls within the native `<input>` — no custom truncation needed for an editable field. |
| long-text | ✅ explicit | Same as overflow — native input behavior, no wrapping concern (single-line field). |
| partial | ✅ explicit | Two partial-input cases, both defined: (a) a 1-character query is *typed but not searched* — the body stays in the hint state and the right-aligned readout reads `"Type to search…"`, not a zero count; (b) a ≥2-character query whose debounce has not yet fired, or whose request is in flight while a *previous* result set is still on screen — the prior results stay rendered and the readout switches to `"Searching…"`. The input is never cleared, disabled, or visually degraded during an in-flight search. |

### E5 — Reveal-to-tree navigation (nav / interactive-control)

| Category | Status | Resolution |
|----------|--------|------------|
| loading | ✅ explicit | If the target hit's catalog is not already loaded, the switch triggers the normal `TreePane` loading path (`23-UI-SPEC.md`'s quiet "Reading {catalog}…" line) before the reveal (expand/select/scroll) can run — the reveal request persists across that gap via `pendingReveal` rather than being dropped. |
| error | ✅ explicit | If the target catalog somehow fails to load between the search returning it as a hit and the user clicking it (e.g. the file was deleted in that window), the tree pane falls back to its existing unreadable-catalog/error surfaces (`23-UI-SPEC.md`, STATE-02) — the reveal request is simply discarded rather than retried or surfaced as a palette-specific error, since the palette has already closed by this point. |
| overflow | ✅ explicit | `scrollToIndex(visibleIdx, { align: 'center' })` — reuses the existing virtualizer instance; no new scroll-region concern beyond what `23-UI-SPEC.md`'s tree contract already covers. |
| zero-one-many | not applicable | A reveal always targets exactly one node. |
| partial | ✅ explicit | **Load-bearing constraint.** A reveal frequently lands in a *partially expanded* tree — the user may already have some of the target's ancestors open, especially when the hit is in the catalog they are already browsing. Ancestor expansion must therefore **set each ancestor to `true`**, never toggle it. Phase 23 shipped `TOGGLE_EXPAND`, which would *collapse* any ancestor that was already open and leave the target invisible — the reveal must use `SET_EXPANDED` (merging the ancestor chain into the existing map) or an equivalent set-semantics action, never a per-ancestor `TOGGLE_EXPAND` loop. Revealing the same node twice in a row must be idempotent, not an open/close flicker. |
| populated | ✅ explicit | The success case: every ancestor of the target is expanded, the target row is selected (adopting the tree's existing selected-row treatment from `23-UI-SPEC.md` — the palette introduces no second selection visual), and the row is scrolled to vertical center. The details panel updates to the revealed node through the same `selected` state it already reads, with no palette-specific path. |
| empty | ✅ explicit | A hit implies the node existed when the search ran, so an empty target is only reachable if the catalog changed on disk in the window between the search returning and the user activating the row. In that case the flat load yields zero nodes, `TreePane` renders its existing empty-catalog state (`23-UI-SPEC.md`), and the pending reveal is **discarded rather than retried** — the palette has already closed and there is nothing left to point at. |
| long-text | ✅ explicit | A deeply nested hit expands a long ancestor chain and selects a row at high indent depth. No new rule is needed: the tree row's existing `min-width: 0` + ellipsis treatment and the breadcrumb's collapse-to-root rule (both `23-UI-SPEC.md`, the latter fixed during Phase 23 execution specifically so a deep selection truncates instead of widening the app) already cover it. The reveal must not introduce horizontal scrolling to make a deep path visible. |
