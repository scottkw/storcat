    - The same path with a different modification time reports a miss.

  <action>
First, in `internal/config/config.go`, extract the config-directory resolution at lines 39-58 into an unexported helper returning the storcat configuration directory path and an error, and have `NewManager` call it. This is a pure extraction with no behaviour change — the existing config tests are the regression gate — and it exists so the cache resolves the same directory rather than growing a second copy that can drift.

Create `internal/config/counts_cache.go`. Define `CountEntry` with `FileCount int` (`fileCount`) and `TotalBytes int64` (`totalBytes`). Define `CountsCache` holding a `sync.Mutex`, the cache file path, and a `map[string]CountEntry`. Export `CountsKey(path string, modTime time.Time, size int64) string`, which joins the path, the modification time formatted as RFC3339 with nanoseconds in UTC, and the size rendered by `strconv.FormatInt`, separated by a vertical bar — a concatenation rather than a hash, which is cheaper to build and collision-safe at this cardinality.

`NewCountsCache()` resolves the shared configuration directory via the helper above, sets the file path to `counts-cache.json` beside `config.json`, and calls `Load`. `Load` reads the file and unmarshals it; a missing file, an unreadable file or invalid JSON all leave an empty map and return no error, because a cache problem must never become a rail problem. `Get` returns the entry and a found boolean. `Put` stores the entry and persists.

Every one of `Load`, `Get` and `Put` takes the mutex for its whole body. This is the single deliberate divergence from `config.Manager`, which has no mutex at all: this cache is written by an opportunistic fill from `LoadCatalogFlat` while the rail may be reading, and Wails does not guarantee that bound methods are invoked serially. Persist by marshalling with `json.MarshalIndent` to match the config file's on-disk style, writing to a temporary file created in the same directory, and renaming it over the target, so a reader can never observe a half-written file. Remove the temporary file if the write or rename fails.

In `internal/config/counts_cache_test.go`, cover every line of the behavior block using `t.TempDir()` and a constructor variant or exported field that lets a test point the cache at a temporary path rather than the user's real configuration directory — do not have tests write to `os.UserConfigDir`. For the concurrency case, run at least 50 goroutines mixing `Put` and `Get` against distinct and overlapping keys, join them with a `sync.WaitGroup`, and assert every key written before the final read is readable. That test is the one this plan runs under the race detector.

Add exactly three fields to `models.CatalogMetadata`, matching the file's existing tag style: `FileCount *int` tagged `fileCount`, `TotalBytes *int64` tagged `totalBytes`, and `ParseError string` tagged `parseError`. The two counts are pointers so the frontend can distinguish "not computed yet" from "genuinely zero" — a cache miss must not render as a confident zero on every rail row. `23-CONTEXT.md` locks the surface at exactly these three; do not add a fourth.

In `internal/search/service.go`, add an unexported `detectParseError(data []byte) string`. It returns an empty string when `json.Valid` accepts the bytes. Only when validity fails does it attempt a real unmarshal, mirroring `LoadCatalog`'s own attempt order (array first, then bare object) so the diagnostic can say which format was tried, and formats a `*json.SyntaxError` as the byte offset followed by the error's own text. `json.Valid` scans without allocating the target structure, so a healthy catalog directory pays one read plus one linear scan per catalog and nothing more — this matters because `BrowseCatalogs` previously never opened a `.json` file at all.

Extend the existing `BrowseCatalogs` loop additively, leaving the title, size, created, modified and HasHtml logic untouched. Read the catalog file's bytes; on a read error set `ParseError` from that error and skip the validity check, so an unreadable file and an invalid one stay distinguishable. Otherwise set `ParseError` from `detectParseError`. Then look up the counts: build the key from the file path, the entry's modification time and its size, and on a hit set both pointer fields; on a miss leave both nil and move on. Never compute counts inline here — a synchronous full parse per catalog is exactly the cost this cache exists to avoid.

Give `Service` an unexported counts-cache field and an exported `SetCountsCache` method. Every cache access must be nil-safe, because `cli/search.go` and `cli/show.go` construct the service with `search.NewService()` and must keep compiling and behaving identically — do not change that constructor's signature.

In `internal/search/flatten.go`, after a successful flatten, opportunistically fill the cache: build the same key from the file's current stat and store the `FileCount` and `TotalBytes` the walk already computed. A failure to persist is ignored; the counts are convenience data.

Extend `internal/search/service_test.go` with a test per line of the behavior block, following the file's existing self-contained fixture style. For the permission-denied case, create the file, remove read permission, restore it with `t.Cleanup`, and skip the test when it runs as root, since root ignores the mode bits. For the allocation claim, add a benchmark over `detectParseError` with allocation reporting for a valid and an invalid document, and assert the relationship in a test using `testing.AllocsPerRun` rather than eyeballing the benchmark.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-23-06 | Tampering | `counts-cache.json`, `internal/config/counts_cache.go` | medium | mitigate | The load-mutate-save cycle is mutex-guarded and persisted through a same-directory temporary file plus rename, so no reader observes a partial write. Any unmarshal failure degrades to an empty map. The cached values are display-only counts — they never feed a path, a filesystem operation or a security decision — so a tampered cache can at worst show a wrong number until the next mtime change invalidates the key. |
| T-23-05 | Tampering | catalog JSON with duplicate or absent keys, `BrowseCatalogs` and `LoadCatalogFlat` | low | accept | Go's decoder takes the last occurrence of a duplicate key and leaves absent keys at their zero value. A node with no type is rejected at the root by plan 23-01's check and renders as a typeless child deeper down; no crash, no injection. Accepted with a test covering the absent-key document rather than a control. |
| T-23-04 | Denial of service | enormous declared `size` values in a catalog | low | accept | Sizes are `int64` in Go and remain exact as JSON numbers below the 2^53 boundary the renderer can represent. A hostile size produces a wrong display figure and nothing else — no allocation is driven by it, because the flattener never allocates from a declared size. |
| T-23-13 | Denial of service | full-content read of every catalog on every rail load | medium | mitigate | `json.Valid` runs before any structural unmarshal, so the common case is one read plus one linear scan. The allocation relationship is asserted in a test rather than assumed. If a directory of very large catalogs ever makes this the bottleneck, the escape hatch named in `23-RESEARCH.md` Pitfall N3 is caching validity beside the counts — deliberately not built now. |
</threat_model>
